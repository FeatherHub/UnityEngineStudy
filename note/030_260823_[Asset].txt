순수 [Serializable] C# class/struct

UnityEngine.Object 를 상속하지 않는 평범한 C# 타입에 [Serializable] 을 붙인 것

핵심 성질은 by value 직렬화
embeds the entire data of the object directly into the serialized data of the object that holds the reference

---

독립 파일로 존재할 수 없고 참조 대상이 될 수 없습니다
리스트에 같은 인스턴스를 두 번 넣으면 사본 두 개가 저장됩니다

이게 ScriptableObject 가 존재하는 이유
데이터 덩어리를 "참조 가능한 것"으로 만들려면 UnityEngine.Object 가 되어야 합니다

managed reference ID 로 추적되어 다형성·null·인스턴스 공유가 가능해집니다
UnityEngine.Object 파생 타입에는 쓸 수 없습니다

PPtr

Persistent Pointer
Internally, Unity represents these references with a PPtr<T> type

public Material Mat; 라고 쓰면 메모리에서는 C# 참조지만
디스크로 나갈 때 그 필드의 표현이 PPtr<Material>

UnityEngine.Object 를 가리키는 모든 직렬화 필드가 그렇습니다

---

GUID 는 128-bit 파일 식별자(.meta 에 저장), 
fileID 는 그 파일 안에서 오브젝트를 식별하는 64-bit ID

빌드된 serialized file 에서는 GUID 가 빠지고 
그 파일의 external reference 테이블 인덱스 + local ID 로 치환됩니다

---

When Unity loads these objects into memory at runtime, 
it resolves the GUID and fileID pair to an InstanceID

---

이 매핑을 담당하는 내부 구조가 PersistentManager 와 Remapper

C++ Object 가 C# UnityEngine.Object 를 가리키고, 
C# 쪽은 instance ID 로 되돌아 연결됩니다

---

PPtr 은 디스크 상의 참조, 
InstanceID 는 메모리 상의 핸들

---

모든 UnityEngine.Object 가 GUID + local file ID 를 가지나?

아니오. persistent object 만 가집니다

GUID 는 파일의 ID 이고 fileID 는 그 파일 안 오브젝트의 ID 입니다
즉 GUID 는 오브젝트의 ID 가 아니라 "그 오브젝트를 담고 있는 에셋 파일의 ID"입니다
프리팹 하나 안의 GameObject 20개는 GUID 를 공유하고 fileID 로 구분됩니다

모든 UnityEngine.Object 가 반드시 갖는 것은 InstanceID 뿐입니다
(Unity 6.4 부터는 Object.GetEntityId 로도 노출)

---

Objects loaded from file will be assigned a positive Instance ID
Newly created objects will have a negative Instance ID
and retain that negative value even if the object is later saved to file

---

그래서 런타임 new GameObject() 는

GUID 없음, fileID 없음
음수 InstanceID 부여
세션이 끝나면 무효 (문서: "The ID changes between sessions of the player runtime and Editor")
씬을 저장하거나 프리팹으로 만드는 순간 비로소 fileID 가 생깁니다 — 단 InstanceID 는 음수 그대로 유지됩니다

---

따라서 InstanceID 부호로 persistent 여부를 판단하면 안 됩니다
EditorUtility.IsPersistent 를 쓰라고 안내합니다

그리고 빌드에는 Asset Database 자체가 없으므로 GUID 라는 개념도 없습니다.

These files contain assets referenced by a scene reference
Their numbering corresponds to the scene in the scene build order

Each instance of a class that derives from UnityEngine.Object 
is linked to a counterpart native object

실제 데이터(mesh 정점, texture 픽셀, transform 행렬)는 C++ 쪽에 있고
C# Material 객체는 그 native object 를 가리키는 얇은 wrapper 입니다

---

The C++ Object has a pointer to the associated C# UnityEngine.Object and
the C# object references back to the associated C++ object via the instance ID

---

디스크    PPtr = (GUID 또는 file index, fileID)
  ↓ 로드 시 resolve
메모리    InstanceID → native C++ Object   ← 여기에 실제 데이터

C# 코드   Material 래퍼 객체 (native 를 가리키는 핸들)

SerializeReference 만 할 수 있는 일

파일을 만들지 않고 다형성을 유지
behavior tree 노드 1000개를 에셋 파일 0개로

null 저장
Value-based serialization can't represent null

순환 그래프
if you serialize a cyclical graph data structure, 
you must use SerializeReference 
to preserve the graph properly 
and to avoid potential freezes or crashes

---

rid 라는 별도 ID 공간 + 타입 이름 직렬화
references 블록에 type: {class, ns, asm} 과 data 가 함께 저장됩니다

타입 이름이 직렬화되니 다형성이 보존되고
ID 가 값과 분리되어 있으니 공유·순환·null 이 표현됩니다

---

참조를 타입 이름으로 붙잡고 있으므로 클래스명·네임스페이스·어셈블리를 바꾸면 끊어집니다

Unity 가 그래서 ManagedReferenceMissingType)과 
SerializationUtility.HasManagedReferencesWithMissingTypes 를 제공합니다

수명 소유권이 GC 에 없다

C# 객체는 GC 가, 
native 객체는 Destroy/씬 언로드/Resources.UnloadUnusedAssets 가 관리합니다. 

서로를 가리키는 독립된 두 수명 시스템입니다

Destroy 후에도 C# 객체가 GC 될 때까지 살아남는 detached state
Texture2D 가 GC 눈에는 수십 바이트인데 실제로는 native 에 수십 MB

---

C# 클래스는 accessor 모음일 뿐입니다

---

MonoBehaviour 와 ScriptableObject 는 데이터 자체가 C# 쪽에 있으므로 
native 객체가 생기는 순간 managed 인스턴스가 함께 생깁니다. 

스크립트 1만 개 붙은 씬은 실제로 managed 객체 1만 개를 만듭니다. 

lazy 인 것은 GameObject, Transform, Renderer, Material, Texture, Mesh 같은 
순수 엔진 타입입니다

오브젝트 1만 개짜리 씬을 로드해도 C# 객체가 1만 개 생기지 않습니다. 
C# 코드가 건드릴 때 만들어집니다

---

IL2CPP 산출물도 여전히 GC 아래서 돌고
write barrier, managed object header 포함 레이아웃

native Unity 객체는 다른 allocator·다른 레이아웃을 씁니다

게다가 icall 경계는 최적화 장벽입니다
IL2CPP 는 그 너머로 인라인하지 않습니다
