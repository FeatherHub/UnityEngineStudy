내 C# 코드
   │
   ├─ [1] managed wrapper 메서드        ← 평범한 C#. JIT 됨
   │       null 검사, 포인터 획득, span 포장, 문자열 해제
   │
   └─ [2] _Injected icall               ← C ABI 함수 호출. 거의 공짜
           IntPtr 와 포인터만 주고받음
              │
              ▼
           C++ 함수

JIT 된 코드는 처음 호출되기 전까지 존재하지 않는다. 
C# 쪽 extern 선언에는 몸통이 없고, 어떤 C++ 함수인지 이름만 있다.

그래서 시작할 때 mono_add_internal_call("UnityEngine.Transform::GetParent_Injected", &실제_C++_함수) 로 
이름→주소 표를 만들어둔다. 
Unity.dll 안의 9,119개 문자열이 이 표

JIT 이 그 메서드를 컴파일할 때 표를 뒤져서 직접 호출로 패치한다
그 뒤로는 그냥 함수 호출

P/Invoke(DllImport)와 다른 점

P/Invoke 는 마샬링 stub 과 관리↔네이티브 전환 처리를 끼운다
internal call 은 그 기계를 건너뛰라고 있는 물건

C# → C++ (internal call)

C# 호출부  →  [JIT 이 이미 주소를 박아둔 직접 호출]  →  C++ 함수

호출 대상이 컴파일 시점에 정해져 있다. 
이름이 metadata 에 박혀 있고 JIT 이 한 번 풀고 나면 끝.

    Java, Kotlin

    C, C++

JNI 는 양방향

Java → native    Java 쪽에 native 키워드로 선언 + System.loadLibrary

native → Java    JNIEnv* 로 FindClass / GetMethodID / CallVoidMethod

---

Android 는 Java 언어와 Java 세계의 규약을 가져왔다. 
다만 실행 포맷은 JVM bytecode 가 아니라 DEX 로 갈아탔고, 
그걸 실행하는 건 JVM 이 아니라 ART 다.

시스템 라이브러리는 관리 코드(Java/Kotlin) API 로 노출된다.

ART 위에서 돌지 않고 CPU 가 직접 실행하는 코드(.so) 를 네이티브 코드라 부른다.

관리 코드와 네이티브 코드가 양방향으로 대화하는 방법을 정한 규약이 JNI 이고, 
이건 Java 세계에서 물려받은 명세를 ART 가 구현한 것이다.

.art   힙 이미지. 자주 쓰는 객체를 미리 만들어둔 것 (부팅·시작 가속)
.vdex  Android 8.0 부터. 검증된 DEX 를 담는 별도 컨테이너

dex2oat  =  "DEX to OAT" 변환 도구
그 변환이 AOT(ahead-of-time) 컴파일

ABI 의 네 층

(1) 플랫폼 ABI        CPU + OS 가 정한다. 아무도 못 바꾼다
                      인자를 어느 레지스터에, 스택 정렬은 몇 바이트,
                      int 는 몇 바이트, 반환값은 어디로
                      문서: System V AMD64 ABI / AAPCS64 / Microsoft x64

(2) 언어 ABI         컴파일러가 정한다  ← C++ 논쟁이 여기
                     이름 맹글링, vtable 배치, 예외 처리, 템플릿 인스턴스화

(3) 표준 라이브러리 ABI   구현체가 정한다
                          std::string 이 몇 바이트이고 멤버가 어떻게 놓이나

(4) 애플리케이션 ABI      내 구조체 배치, 내 인터페이스 설계

C ABI

int add3(int a, int b, int c) {
    return a + b + c;
}

0:   f3 0f 1e fa     endbr64
4:   01 f7           add    %esi,%edi
6:   8d 04 17        lea    (%rdi,%rdx,1),%eax
9:   c3              ret

---

a 는 edi 레지스터에 들어와 있다고 가정한다
b 는 esi 레지스터에
c 는 edx 레지스터에
결과는 eax 레지스터에 넣고 나간다

그런데 이 약속을 누가 정했나? 
C 언어가 아니다. CPU 와 OS 가 정했다

x86-64 리눅스에는 System V AMD64 ABI 라는 문서가 있고,
거기에 "정수 인자는 rdi, rsi, rdx, rcx, r8, r9 순서로 넣는다" 가 있다

ARM64 는 AAPCS64 라는 문서가 x0~x7 을 쓰라고 정한다

컴파일러는 그 문서를 따를 뿐이다
