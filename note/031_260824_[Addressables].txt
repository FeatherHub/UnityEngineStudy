밑바탕: GUID + fileID 직렬화

Unity는 에셋을 경로가 아니라 GUID(.meta 파일에 기록) + local fileID 쌍으로 참조

런타임 오브젝트 간 참조는 PPtr로 직렬화

"에셋 로딩"이란 결국 이 PPtr 그래프를 어떻게 파일에서 복원할 것인가의 문제

---

Resources 폴더

Resources.Load("path").

Resources 폴더 안의 모든 것이 참조 여부와 무관하게 빌드에 포함되고
하나의 resources.assets로 합쳐짐

앱 시작 시 전체 lookup 인덱스를 구축해야 해서 폴더가 커질수록 기동 시간이 선형으로 증가

빌드에 박히므로 패치 불가, 플랫폼별 교체 불가

사실상 프로토타이핑/소형 프로젝트 전용

Addressables (2018.2 preview → 2019 정식) — 현재의 표준

"어느 번들에 있는지 신경 쓰지 말고 주소로 부르라"

로컬/원격을 그룹 설정만으로 전환
코드 수정 없이 CDN 배포 가능

Content Update Workflow

Build Layout 리포트로 번들 내용 분석

raw 데이터 분리

텍스처 픽셀은 역직렬화 없이 GPU로 바로 업로드하고
오디오는 부분 스트리밍하고

---

Uncompressed
가장 크고 가장 빠릅니다
파일을 그대로 메모리 매핑할 수 있어 로드 시 CPU가 거의 들지 않습니다.

LZMA 
스트림 전체를 하나로 압축합니다
가장 작지만 일부만 꺼내 읽을 수 없어 전체를 해제해야 합니다
다운로드 대역폭이 병목인 원격 배포용이고
받은 뒤에는 재압축해서 보관합니다

LZ4 / ChunkBasedCompression
128KB 청크 단위 압축
필요한 청크만 해제하므로 랜덤 액세스가 가능합니다
"압축했는데도 빠른" 조합이라 로컬 기본값입니다.

JSON catalog
본문이 base64 이진 blob 네 개

m_KeyDataString — 모든 key. address, label, GUID 문자열이 전부 여기

m_EntryDataString — 엔트리 레코드 배열. 실제 location 정보
m_ExtraDataString — provider별 부가 데이터

Addressables

에셋을 이름으로 요청하면, 
어디에 있든, 필요한 것만 가져오고, 
다 쓰면 알아서 치워주는 시스템

---

앱 크기. 스토어 용량 제한이 있고, 초기 다운로드가 크면 유저가 이탈합니다.
메모리. 특히 모바일에는 상한이 있고, 넘으면 그냥 죽습니다.
업데이트. 콘텐츠를 바꾸려고 매번 앱 심사를 받을 수는 없습니다.

에셋을 빌드 밖으로 빼두고, 필요할 때 가져온다.

"빌드 밖으로 뺀 에셋 덩어리"가 곧 AssetBundle

이름과 실제 위치 사이에 사전(catalog) 을 하나 끼워 넣은 것

코드가 위치를 모르니 → 에셋을 옮기고 번들을 재편해도 코드가 안 바뀜
사전을 교체할 수 있으니 → 앱 업데이트 없이 콘텐츠 교체
사전이 의존성을 알고 있으니 → 의존 번들 자동 로드
