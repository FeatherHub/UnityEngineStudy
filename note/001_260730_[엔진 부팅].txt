3. EarlyUpdate

UnityWebRequest 처리, 
메인스레드 잡 실행, 
에셋 스트리밍/프리로딩 갱신, 
구 Input Manager 갱신

4. FixedUpdate
고정 시간 스텝 구간

시뮬레이션 시간이 실제 시간을 따라잡을 때까지 
한 프레임에 0~N회 반복됩니다

ScriptRunBehaviourFixedUpdate(MonoBehaviour.FixedUpdate)
Director/애니메이션 fixed 갱신
PhysicsFixedUpdate(3D 물리 시뮬레이션 스텝) → Physics2D → Cloth → ScriptRunDelayedFixedFrameRate(WaitForFixedUpdate 코루틴 재개)

즉 내 FixedUpdate 코드가 물리 스텝보다 먼저 돌아서, 힘을 가한 뒤 시뮬레이션되는 구조
OnCollision/OnTrigger류는 물리 스텝 내부(네이티브)에서 호출

---

5. PreUpdate

PhysicsUpdate(보간된 Transform 동기화 등 물리 후처리), 
새 Input System 갱신(NewInputUpdate),

AIUpdate(NavMesh), 
비디오 갱신

---

6. Update

ScriptRunBehaviourUpdate(MonoBehaviour.Update)
ScriptRunDelayedDynamicFrameRate(yield return null / WaitForSeconds 코루틴 재개 — 코루틴이 "Update 다음"에 도는 지점) 
→ ScriptRunDelayedTasks(async/await가 메인스레드로 돌아오는 UnitySynchronizationContext 연속 실행) 
→ DirectorUpdate(Timeline)

---

7. PreLateUpdate 
애니메이션의 페이즈

DirectorUpdateAnimationBegin~End 사이에서 Animator 평가

UI Toolkit 패널 업데이트
파티클 시작
그리고 마지막에 ScriptRunBehaviourLateUpdate(MonoBehaviour.LateUpdate)

애니메이션 평가가 끝난 후에 LateUpdate가 오기 때문에 
카메라 추적 코드를 LateUpdate에 두는 것

---

8. PostLateUpdate

uGUI(RectTransform/캔버스),

IL은 실존하지 않는 추상 스택 머신 (가상의 CPU 명령어 세트)을 겨냥해 쓰인 코드고, 
C# 컴파일러는 그 상상의 기계를 목표로 컴파일

런타임의 임무는 진짜 하드웨어가 그 상상의 기계처럼 행동하게 만드는 것

한 줄씩 흉내 내기(인터프리터 — Mono에 실제로 이 모드도 있고, "VM"이라는 이미지의 역사적 기원)
통째로 번역해두기(JIT/AOT — 현재의 기본)

C# 소스 → IL + 메타데이터 = 어셈블리

IL2CPP 경로: IL ─ (빌드 시) → C++ ─ (플랫폼 컴파일러) → 바이너리 속 기계어

어느 경로든 최종 실행: CPU

---

C++는 컴파일러마다 이름 장식(name mangling), vtable 배치, 예외 처리 방식이 달라서 
컴파일러 경계를 넘는 표준 규약이 없습니다. 

반면 C의 함수 호출 규약은 사실상 만국 공통어라, 
"누가 만든 무엇이든 나를 호출할 수 있어야 하는" 라이브러리는 
전부 extern "C"로 문을 냅니다
Vulkan, SQLite, Python C API가 다 그렇습니다

언리얼에 이런 문이 없는 이유도 이제 자명하죠
게임 C++는 엔진과 같은 언어, 같은 컴파일러로 함께 빌드되어 직접 링크되니까 
외국어용 출입문이 필요 없는 겁니다

---

런타임

① 실행 시점(runtime vs compile time)
② 어떤 언어를 실행시켜주는 지원 소프트웨어(the C# runtime = Mono)
③ C 언어의 표준 지원 라이브러리인 CRT(C runtime — malloc, printf를 제공하는 층, 모든 네이티브 프로그램이 링크)

런타임이 봉사하는 언어와 런타임이 만들어진 언어는 별개

C#을 실행시켜주는 기계 장치가 C#으로만 쓰여 있다면 닭과 달걀 문제 
누군가는 먼저 네이티브로 존재해야 하죠

OS가 메모리를 관리하는 단위(보통 4KB)
페이지마다 읽기/쓰기/실행 권한이 붙습니다

바이너리 속 기계어
빌드 때 파일(.exe/.dll)의 코드 섹션에 새겨진 것
프로세스 시작 시 OS 로더가 그 파일을 메모리에 매핑

실행 페이지의 기계어는 실행 중에 태어난 것
JIT가 OS에서 빈 페이지를 받아(VirtualAlloc/mmap), 
거기에 방금 생성한 기계어 바이트를 써넣고, 
페이지 권한을 실행 가능으로 바꿉니다

---

iOS가 JIT를 금지하는 방법

일반 앱에게 "쓰기 가능했던 페이지를 실행 가능으로 바꾸는 것"을 허용하지 않는 것

---

JIT 산출물은 어디에 저장

GC 힙(C# 객체용)도, malloc 힙(일반 네이티브 데이터용)도 아니고, 
JIT가 따로 운영하는 코드 캐시

OS에서 직접 페이지를 받아 실행 권한을 부여해 관리하는 전용 풀

실행 권한이 필요하고(데이터 힙은 보안상 실행 불가가 원칙
W^X: 쓰기와 실행을 동시에 주지 않는 규칙)

트램폴린 패치 같은 특수 작업이 있고, 수명도 다릅니다. 
한 번 컴파일된 메서드의 기계어는 보통 프로세스가 사는 동안 유지되고 재사용됩니다.
