uGUI (Unity 4.6, 2014년 11월)

retained mode
UI가 씬에 GameObject로 존재하고, 상태를 유지하며, 바뀐 부분만 갱신

---

Canvas, CanvasRenderer, CanvasGroup, RectTransform
네이티브 C++ 모듈(UIModule)이고

Image·Button·ScrollRect 같은 실제 UI는 전부 C# 패키지
com.unity.ugui 패키지  

Unity 6에서는 TextMeshPro가 이 패키지로 흡수
기존 com.unity.textmeshpro는 껍데기(shim)만

---

화면에 뭔가 그리는 모든 것은 Graphic 추상 클래스를 상속

핵심은 Graphic::OnPopulateMesh(VertexHelper)
여기서 정점을 채우면 그 결과가 CanvasRenderer.SetMesh로 넘어갑니다

Image는 사각형 4개 정점
Text는 글자마다 사각형을 채우는 식

---

확장점

IMeshModifier는 만들어진 정점을 후처리하고(Outline, Shadow가 이걸로 구현),
IMaterialModifier는 최종 머티리얼을 가로챕니다(Mask가 스텐실 머티리얼을 끼워넣는 데 사용)

---

Graphic은 dirty 플래그가 3종

SetVerticesDirty(모양 변경)
SetMaterialDirty(재질 변경)
SetLayoutDirty(크기 영향)

더러워진 요소는 CanvasUpdateRegistry라는 싱글턴 큐에 등록되고
이 큐는 Canvas.willRenderCanvases(네이티브가 캔버스를 그리기 직전에 부르는 콜백)에 물려서 한 번에 처리

---

Prelayout → Layout → PostLayout → 컬링(ClipperRegistry) → PreRender → LatePreRender

레이아웃 큐는 처리 전에 부모 개수(계층 깊이) 기준으로 정렬
부모가 자식보다 반드시 먼저 계산되게 하려는 것으로
트리 순회 대신 정렬로 푸는 해법

---

ILayoutElement가 "나는 최소 이만큼, 이상적으로 이만큼, 남으면 이 비율로 더" 
(min/preferred/flexible)를 보고

ILayoutController가 실제로 자식 위치를 정합니다. 

실행 순서는 가로 계산 → 가로 배치 → 세로 계산 → 세로 배치

가로를 먼저 확정하는 이유는 텍스트 줄바꿈 때문
폭이 정해져야 몇 줄인지 알고, 그래야 높이가 나옵니다.

---

EventSystem

UI 컴포넌트와 분리된 별도 체계

BaseInputModule(StandaloneInputModule 등)이 입력을 읽고, 
BaseRaycaster(GraphicRaycaster는 UI, PhysicsRaycaster는 3D 콜라이더)가 대상을 찾고, 
ExecuteEvents가 IPointerClickHandler 같은 인터페이스를 구현한 컴포넌트에게 전달

상속이 아니라 인터페이스라서 아무 MonoBehaviour나 UI 이벤트를 받을 수 있습니다.

---

Mask는 스텐실 버퍼(GPU가 픽셀별로 갖는 도장 같은 버퍼)를 써서 임의 모양으로 자르지만 드로우콜이 늘어납니다. 

RectMask2D는 셰이더에 사각형 좌표만 넘겨 잘라내서 훨씬 싸지만 사각형만 됩니다. 
ScrollView가 후자를 쓰는 이유

갱신 개념
페이즈 분리와 비트 플래그

uGUI의 dirty 플래그가 3종이었다면
여기는 VersionChangeType이 20종이 넘는 비트 플래그

그리고 갱신 파이프라인이 페이즈별로 나뉘어 각각 전담 updater를 갖습니다

ViewData → Bindings → DataBinding → Animation → Styles → Layout → TransformClip → Repaint → Authoring

색만 바꾸면 Color 비트만 서고 Repaint 페이즈만 돌아갑니다

레이아웃을 건드리지 않는 변경이 레이아웃을 재계산하지 않는다는 뜻으로

레이아웃 개념 — Flexbox

Yoga(Facebook이 만든 Flexbox 구현체)를 가져와 변형한 것이 출발점

flex-direction, flex-grow, flex-shrink, flex-basis, align-items, justify-content 등 
웹 Flexbox 개념이 그대로 이름까지 같습니다

실제 계산은 네이티브 프로세서로 내려가는 데이터 지향 구조

이벤트 개념 — DOM식 전파

uGUI가 "레이캐스트로 찾은 대상에게 직접 호출"이었다면, 
여기는 웹 DOM과 같은 3단계

루트에서 대상까지 내려가는 TrickleDown(웹의 capture), 대상에서의 AtTarget, 다시 루트로 올라가는 BubbleUp

중간 어느 요소에서든 가로채거나 멈출 수 있어서, 
부모가 자식 무리의 이벤트를 한 곳에서 처리하는 패턴이 자연스럽습니다.

---

렌더링

Canvas/CanvasRenderer를 쓰지 않고 전용 렌더러를 씁니다. 

자체 아틀라스 할당기가 있고, 
RenderHints/UsageHints로 개발자가 최적화 힌트를 명시

예를 들어 "이 요소는 매 프레임 위치가 바뀔 것"(DynamicTransform), 
"이 서브트리는 통째로 움직임"(GroupTransform)이라고 알려주면 배칭을 깨지 않고 처리

uGUI에서 Canvas를 쪼개서 암묵적으로 하던 일을 명시적 API로 만든 셈

---

uGUI 패키지 안에 PanelRaycaster와 PanelEventHandler가 들어 있습니다. 

UI Toolkit 패널을 uGUI의 EventSystem에 참여시키는 다리로, 
한 프로젝트에서 두 시스템을 섞어 쓸 때 입력 순서가 꼬이지 않게 합니다. 

반대로 UI Toolkit 단독으로 쓸 때를 위한 자체 이벤트 시스템도 별도로 있습니다.

Graphic — "그리는 것"의 최소 정의

---

메시가 공유물

Graphic::workerMesh는 "Shared UI Mesh"라는 이름의 static Mesh 하나
VertexHelper도 static 하나

Graphic이 수천 개여도 C# 쪽 Mesh 객체는 1개

메시는 소유물이 아니라 전달 매체
정점을 채워서 CanvasRenderer.SetMesh로 네이티브에 넘기는 순간 C# 쪽은 그 내용을 잊습니다

실제 보관은 네이티브가 합니다. 
덕분에 GC 압력이 거의 없지만, 대가로 메시 생성은 원리적으로 병렬화할 수 없습니다
공유 버퍼 하나를 순차적으로 돌려쓰는 구조

Material(재질), 
Layout(크기 영향).

---

바로 계산하지 않고 큐에 넣는 이유

한 프레임에 같은 요소를 100번 바꿔도 rebuild는 1회

---

큐 자료구조가 IndexedSet
List와 Dictionary를 같이 들고 있는 물건

중복 없는 삽입이 O(1), 
제거는 마지막 원소를 빈자리로 옮겨서 O(1)

대신 순서가 보장되지 않습니다

그래서 레이아웃 큐는 처리 직전에 매번 정렬합니다.

컬링이 레이아웃과 렌더 사이에 끼어 있는 게 설계 의도
최종 크기가 확정돼야 잘릴지 판단할 수 있고

---

두 인터페이스

ILayoutElement — 나는 최소 이만큼, 이상적으로 이만큼, 남으면 이 비율로 더 
(min/preferred/flexible + layoutPriority). 
위로 보고만 합니다

ILayoutController — 실제로 rect를 정합니다. 아래로 지시만 합니다
  ILayoutGroup: 자식을 제어
  ILayoutSelfController: 자기 자신을 제어 (ContentSizeFitter, AspectRatioFitter)
  ILayoutIgnorer: 계산에서 제외

이 분리 덕분에 새 컴포넌트가 둘 중 하나만 구현해도 시스템에 참여합니다
Text가 "내 선호 크기는 이만큼"만 보고하면 어떤 LayoutGroup 아래서든 동작

---

네 패스

LayoutRebuilder::Rebuild가 순서대로 이렇게 부릅니다.

  CalculateLayoutInputHorizontal — 자식에서 부모로 (bottom-up)
  SetLayoutHorizontal — 부모에서 자식으로 (top-down)
  CalculateLayoutInputVertical — bottom-up
  SetLayoutVertical — top-down

방향이 번갈아 나오는 건 정보의 흐름이 반대이기 때문
필요한 크기는 아래에서 위로 모이고, 
실제 배분은 위에서 아래로 흐릅니다.

---

가로와 세로를 분리한 이유는 텍스트

폭이 확정돼야 줄바꿈이 결정되고, 
줄 수가 나와야 높이를 계산할 수 있습니다. 

배분 규칙은 min 먼저 채우고, 남으면 preferred까지, 더 남으면 flexible 비율대로입니다.

layout root — 레이아웃 재계산의 단위

LayoutRebuilder::MarkLayoutForRebuild

요청받은 RectTransform에서 부모를 거슬러 올라가며 
활성 ILayoutGroup을 가진 가장 위 조상을 찾고, 
큐에 등록하는 건 그 루트 하나

즉 레이아웃 재계산의 최소 단위는 개별 요소가 아니라 레이아웃 그룹 체인 전체

3중첩 VerticalLayoutGroup 맨 안쪽 라벨의 텍스트가 한 글자 바뀌면, 
최상위 그룹부터 전부 다시 계산됩니다. 

중첩 Layout Group이 성능 문제로 악명 높은 이유가 이 한 줄기 로직에 있습니다

반대 방향의 가지치기도 있습니다.

DrivenRectTransformTracker — 계산값과 저작값의 구분

LayoutGroup, ContentSizeFitter, Slider, Scrollbar, ScrollRect, AspectRatioFitter가 전부 이걸 씁니다
자기가 자식의 어떤 속성을 "점유"했는지 등록하는 장치

효과가 두 가지입니다. 인스펙터에서 그 필드가 회색으로 잠기고, 씬/프리팹 저장 시 그 값이 diff에 남지 않습니다
시스템이 계산한 값과 사람이 저작한 값을 구분하는 메커니즘으로

없으면 레이아웃이 돌 때마다 씬 파일이 더러워집니다.

Mask는 IMaterialModifier

스텐실 버퍼(GPU가 픽셀마다 갖는 도장 같은 버퍼)

중첩 깊이마다 비트를 하나씩 소비하므로 최대 8단계

마스크 영역을 세우는 머티리얼과 
되돌리는 머티리얼을 push/pop 쌍으로 발행

임의 모양이 가능하지만 드로우콜이 늘고 배칭이 깨집니다.

---

RectMask2D는 IClipper

머티리얼을 건드리지 않고 셰이더에 클립 사각형만 넘깁니다

여러 RectMask2D가 겹치면 사각형 교집합을 계산하고, 
클립 영역을 완전히 벗어난 자식은 canvasRenderer.cull = true로 아예 제외

softness(가장자리 알파 페이드)도 여기서 나옵니다.

---

Mask는 머티리얼 파이프라인에 개입하고, 
RectMask2D는 캔버스 갱신 루프에 개입합니다. 

후자가 훨씬 싼 건 붙는 위치가 다르기 때문

---

IClippable/IClipper 인터페이스 쌍이 별도로 있어서, 
마스크 대상이 MaskableGraphic이 아니어도 클리핑에 참여할 수 있습니다.

유니티에서 "그린다"

Mesh — 정점 위치, 색, UV, 삼각형 인덱스. "무엇을 그릴지"
Material — 셰이더와 그 파라미터. "어떻게 그릴지"

public static bool Execute<T>(GameObject target, BaseEventData eventData, EventFunction<T> functor)

제네릭 T만으로는 "어떤 메서드를 부를지" 알 수 없다.

그래서 "T를 받아서 무엇을 할지"를 델리게이트로 같이 넘깁니다.

// ExecuteEvents - 미리 만들어둔 정적 델리게이트 (매번 람다를 할당하지 않으려고)
private static readonly EventFunction<IPointerClickHandler> s_PointerClickHandler = Execute;

private static void Execute(IPointerClickHandler handler, BaseEventData eventData)
{
    handler.OnPointerClick(ValidateEventData<PointerEventData>(eventData));
}

SDF(Signed Distance Field)

보통 폰트 텍스처는 픽셀마다 "여기가 글자 안이면 흰색, 밖이면 투명"을 저장합니다.
저장된 것이 경계라서, 확대하면 그 경계도 같이 뭉개집니다.

SDF는 픽셀마다 가장 가까운 글자 윤곽선까지의 거리를 저장합니다. 
안쪽이면 양수, 바깥이면 음수

거리는 위치에 대해 부드럽게 변하는 값입니다. 
그래서 텍스처를 확대해 선형 보간해도 그 값이 여전히 의미를 갖습니다

---

경계 판정 기준값을 옮기면 → 글자가 굵어지거나 얇아짐 (볼드)
두 기준값 사이를 다른 색으로 칠하면 → 외곽선
좌표를 조금 밀어서 다시 판정하면 → 그림자
바깥쪽 거리로 그라디언트를 주면 → 발광

public class HudController : MonoBehaviour
{

C# 코드는 무엇이 되나

Mono 백엔드 — IL을 그대로 두고 런타임에 JIT 컴파일
IL2CPP 백엔드 — IL을 C++ 소스로 변환한 뒤 네이티브로 컴파일

---

에디터는 항상 Mono
The Unity Editor embeds Mono

빌드의 기본값은 IL2CPP가 아닙니다
When a platform can support both backends, Mono is the default

---

IL2CPP가 강제되는 경우

JIT 컴파일을 허용하지 않는 플랫폼 — iOS, 콘솔, WebGL 계열
출시 빌드에서는 실행 성능과 코드 보호 때문에 지원 플랫폼에서도 IL2CPP로 바꾸는 경우

---

Mono — Assembly-CSharp.dll이 그대로 빌드에 실려 나가고, 런타임에 JIT 컴파일됩니다. 
빌드가 빠르고 반복 개발에 유리하지만, dll을 추출해 디컴파일하기가 쉽습니다.

IL2CPP — IL을 C++ 소스로 변환한 뒤 플랫폼 컴파일러로 네이티브 컴파일합니다. 
빌드가 느리지만 실행이 빠르고 리버싱이 어렵습니다.

---

브라우저의 네이티브 엔진(렌더링, 네트워크, 레이아웃) ↔ Unity의 네이티브 엔진(렌더링, 물리, 오디오)
JS 런타임(V8) ↔ 스크립팅 백엔드(Mono 또는 IL2CPP 런타임)
웹페이지(HTML·CSS·JS 묶음) ↔ 프로젝트(씬·에셋·스크립트 묶음)
