C# 어트리뷰트

어셈블리 메타데이터에 직렬화되어 저장되는 선언적 데이터
실행되는 코드가 아니다

컴파일러는 [Retry(3)]를 보면 IL 명령을 만들지 않고, 
어셈블리의 CustomAttribute 메타데이터 테이블에 
"이 메서드에 RetryAttribute 생성자를 인자 3으로 호출하는 레시피가 붙어 있다"는 blob을 기록한다. 
실제 객체는 누군가 리플렉션으로 조회할 때 생성된다

---

인자는 반드시 컴파일 타임 상수여야 한다
기본형, string, Type, enum, 그리고 이들의 1차원 배열

어트리뷰트는 스스로 아무것도 하지 않는다
이를 읽어 해석하는 소비자(런타임 프레임워크, 컴파일러, 소스 제너레이터)가 있어야만 의미가 생긴다

---

[AttributeUsage(AttributeTargets.Class | AttributeTargets.Method,
                AllowMultiple = false,
                Inherited = true)]
public sealed class RetryAttribute : Attribute
{
    public RetryAttribute(int count) => Count = count;  // 위치 인자
    public int Count { get; }
    public int DelayMs { get; set; } = 100;             // 명명 인자
}

System.Attribute를 상속한 평범한 클래스
생성자 매개변수는 위치 인자가 되고,
public 설정 가능 프로퍼티/필드는 명명 인자가 된다.

[Retry(3, DelayMs = 500)]
public void Fetch() { }

관례상 이름을 ~Attribute로 끝내면 사용 시 접미사를 생략할 수 있다

sealed를 붙이는 이유는 조회 성능 때문이다
런타임이 상속 계층을 탐색하지 않아도 된다

attr.Count

컴파일 타임 소비 (Roslyn)

소스 제너레이터와 애널라이저는 심볼 단계에서 ISymbol.GetAttributes()로 읽고, 결과 코드를 미리 생성한다

컴파일러가 해석하는 어트리뷰트

[Obsolete] → 경고/에러 발생
[Conditional("DEBUG")] → 심볼이 없으면 호출부 자체를 제거
[CallerMemberName] → 호출자 이름을 컴파일 타임에 주입
[NotNullWhen(true)] 등 → nullable 흐름 분석에 반영

Java Annotation

C#은 진짜 클래스
생성자, 프로퍼티, 메서드, 로직도 넣을 수 있다
Java의 @interface는 인터페이스 유사 선언이고, 요소는 메서드 시그니처 형태로 쓴다.

@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.TYPE, ElementType.METHOD})
public @interface Retry {
    int value();
    int delayMs() default 100;
}

인스턴스화

C#은 조회 시점에 실제 생성자를 호출한다. 
Java는 컴파일러가 만든 동적 프록시를 돌려주며, 생성자 개념 자체가 없다. 
따라서 Java 어노테이션은 상속도 불가능하고, 어노테이션 안에 계산 로직을 넣을 수 없다

위치 인자
C#은 생성자 덕분에 자연스럽게 지원한다. 
Java는 명명 요소만 있으며, 
단일 요소일 때 이름을 value로 지으면 @Retry(3)처럼 생략 가능한 게 전부

---

보존 정책
Java는 @Retention(SOURCE / CLASS / RUNTIME)으로 어디까지 남길지 정한다
C#은 기본적으로 항상 메타데이터에 남으며, 
유사 효과는 어트리뷰트 클래스에 [Conditional]을 붙여 조건부 방출을 막는 방식으로만 낸다

---

반복과 상속
C#은 AttributeUsage(AllowMultiple, Inherited) 로 처리한다. 
Java는 Java 8의 @Repeatable이 컨테이너 어노테이션 타입을 따로 요구하고, 
@Inherited는 클래스 상속에만 적용되며 인터페이스에는 전파되지 않는다

---

타입 사용 위치
Java 8은 TYPE_USE를 도입해 List<@NonNull String>처럼 
타입이 나타나는 모든 자리에 붙일 수 있게 했다. 
Checker Framework 같은 점진적 타입 검사기의 기반
C#에는 이 개념이 없고, 대신 nullable 참조 타입을 언어 기능으로 흡수했다.

어트리뷰트는 타입 시스템 밖의 세계다. 
잘못 붙여도 대개 컴파일이 통과하고 런타임에 조용히 무시된다. 

어트리뷰트끼리 합성하거나 추상화할 수도 없다
여러 어트리뷰트를 하나로 묶는 표준적 방법이 없다

Attribute 인자에서 왜 struct는 제외되었나

struct는 커스텀 생성자, private 불변식, [StructLayout]을 가질 수 있다. 
이걸 복원하려면 생성자를 실행
메타데이터를 훑기만 하는 도구가 임의 코드를 실행하게 된다. 
ildasm, MetadataLoadContext, 링커, 소스 제너레이터 모두 CLR 위에서 사용자 코드를 돌릴 수 없거나 돌려서는 안 되는 주체다

아니면 생성자를 우회해 필드에 직접 값을 꽂거나
캡슐화와 불변식 파괴

---

[MyAttr(1.5m)]                     // 컴파일 에러
[MyAttr(new DateTime(2026, 1, 1))] // 컴파일 에러

우회로

[DecimalConstant(1, 0, 0u, 0u, 15u)]   // scale, sign, hi, mid, low → 정수 5개
[DateTimeConstant(638000000000000000)] // long ticks 하나

struct를 넣을 수 없으니 정수로 분해해서 넣고 소비자가 재조립

어노테이션 안에 로직을 넣을 수 있는가

Java 어노테이션의 멤버는 본문 없는 추상 접근자 선언
생성자도, 필드도, 정적 메서드도, 구현 메서드도 못 넣는다
런타임 인스턴스는 컴파일러가 만든 Map<String, Object> 기반 동적 프록시

Java의 Bean Validation은 이걸 못 해서 @NotNull과 별도로 
ConstraintValidator<NotNull, Object> 구현 클래스를 만들고 
@Constraint(validatedBy = ...)로 연결한다. 

---

붙어 있는 어노테이션이 하위 클래스에 보이는가

@Inherited는 위 두 축과 아무 상관이 없다
class B extends A이고 A에 @Foo가 붙어 있을 때, B.class.getAnnotation(Foo.class)가 그걸 돌려주는가?

extends(클래스 상속)에만 적용된다. implements로는 절대 전파되지 않는다

클래스 타겟에만 의미가 있다. 
메서드나 필드에 붙은 어노테이션은 @Inherited가 있어도 오버라이드로 전파되지 않는다

getAnnotations()에만 영향을 준다. 
getDeclaredAnnotations()는 언제나 직접 붙은 것만 본다

---

C#은 오버라이드된 메서드와 프로퍼티에도 전파된다
반면 인터페이스를 훑지 않는 건 양쪽 다 같다

class Base { [My] public virtual void M() { } }
class Derived : Base { public override void M() { } }

typeof(Derived).GetMethod("M").GetCustomAttribute<MyAttribute>(inherit: true);
// → 찾는다.

프로퍼티와 이벤트에 대해 inherit을 무시하는 것으로 알려져 있어, 
이 경우 정적 메서드 Attribute.GetCustomAttributes(...) 쪽을 쓰는 편이 안전

메타데이터 힙

컴파일 시점에 확정되는 읽기 전용 바이트 풀이
내부 구조가 없다. 테이블 행이 오프셋으로 찔러야 비로소 "여기부터 저기까지가 하나의 문자열"이 된다
중복 제거된다. 같은 문자열이 백 번 쓰여도 힙에는 한 번만 들어가고 백 개의 행이 같은 오프셋을 가리킨다

---

#Strings — 바이트 오프셋. UTF-8 null 종료. 오프셋 0은 빈 문자열
#Blob — 바이트 오프셋. 각 항목이 압축 길이 접두사를 갖는다
#US — 바이트 오프셋. UTF-16, ldstr이 쓰는 사용자 문자열
#GUID — 예외적으로 1부터 시작하는 레코드 번호다. 16바이트 고정이라 오프셋을 쓸 이유가 없다

COFF header (IMAGE_FILE_HEADER, 20바이트)
Common Object File Format
유닉스 System V에서 온 포맷

PE는 사실상 COFF의 확장판이라
헤더 이름이 그대로 남았다

담긴 정보는 "이 바이너리가 무엇인가"에 대한 최소 신원 정보

Machine — 대상 아키텍처 (0x014C = x86, 0x8664 = x64, 0xAA64 = ARM64)
NumberOfSections — 섹션 헤더 배열의 길이
TimeDateStamp — 빌드 시각. 결정적 빌드에서는 시각 대신 내용 해시가 들어간다
Characteristics — 플래그. EXECUTABLE_IMAGE, DLL, LARGE_ADDRESS_AWARE 등

---

RVA = Relative Virtual Address
모듈이 메모리에 적재된 뒤의 베이스 주소로부터의 상대 오프셋

실제 주소 = 실제 로드 주소 + RVA

디스크 배치와 메모리 배치가 다르기 때문

섹션은 디스크에서 FileAlignment(보통 512바이트)로 정렬되지만 
메모리에서는 SectionAlignment(보통 4096, 페이지 크기)로 정렬된다.

같은 섹션이 디스크 오프셋 0x200에 있어도 메모리 오프셋은 0x1000이 된다
그리고 ASLR 때문에 실제 로드 주소는 실행할 때마다 달라진다

RVA는 이 두 변수를 모두 소거한 안정 좌표

.text라는 이름은 유닉스 전통
프로그램의 명령어 부분을 "text segment"라 불렀고 
COFF가 그 이름을 물려받았다. 

하지만 섹션 이름은 관례일 뿐 강제되지 않는다
실제로 의미를 갖는 건 섹션 헤더의 Characteristics 플래그이고, .
text는 보통 MEM_READ | MEM_EXECUTE | CNT_CODE로 매핑된다.

관리 어셈블리의 .text에 실제로 들어가는 것

CLI 헤더
메타데이터 전체 (모든 스트림과 힙과 테이블)
IL 메서드 본문 
강한 이름 서명
임베드 리소스

왜 다 몰아넣는가
전부 읽기 전용에 불변이기 때문
페이지 보호 속성이 같으면 섹션을 나눌 이유가 없다
나누면 4KB 정렬 낭비만 생긴다

코드화 인덱스 (coded index)

CustomAttribute.Parent는 22개 테이블 중 어디든 가리켜야
순진하게 하면 "테이블 식별자 1바이트 + 행 번호 4바이트" = 5바이트
어셈블리 하나에 어트리뷰트 적용이 수만 개인데 이건 낭비

해법은 하나의 정수 안에 하위 비트로 태그를 밀어 넣는 것이다.

후보 테이블 22개 → 태그 비트 ⌈log₂ 22⌉ = 5비트

값     = 0x0083 = 0b0000_0000_1000_0011
태그   = 0x83 & 0x1F = 0b00011 = 3   → TypeDef 테이블
행     = 0x83 >> 5   = 0b100   = 4   → 그 테이블의 4번 행

[...]를 문법적으로 붙일 수 있는 대상

Module

TypeDef — 이 모듈이 정의한 모든 타입
Field / MethodDef 
Param
Property / Event
GenericParam - 제네릭 매개변수 T 자체
GenericParamConstraint— where T : IComparable 의 개별 제약
InterfaceImpl— "타입 X가 인터페이스 Y를 구현한다"는 쌍, 인터페이스 구현 하나하나에 어트리뷰트를 붙일 수 있다

---

TypeRef — 외부 타입 참조. 이름 + ResolutionScope(어느 어셈블리에서 왔는지)
MemberRef — 외부 멤버 참조
ModuleRef — 외부 모듈. [DllImport("user32.dll")]의 "user32.dll"이 여기 들어간다
AssemblyRef — 참조 어셈블리. 이름, 버전, 컬처, 공개키 토큰. 이 테이블이 곧 의존성 목록이다

---

Assembly — 어셈블리 정체성. 이름, 버전, 해시 알고리즘, 공개키. 행 하나. [assembly: ...]의 대상
File — 다중 모듈 어셈블리의 구성 파일 목록과 해시
ExportedType — 타입 포워딩. "이 이름의 타입은 저쪽 어셈블리에 있다"
ManifestResource — 임베드 리소스의 이름, 오프셋, 가시성

---

TypeSpec — 구성된 타입. List<int>, int[], T*처럼 이름이 없고 시그니처로만 표현되는 타입. 
List<int>는 TypeDef가 아니다 — 정의된 건 List<T>뿐이고 List<int>는 blob에 인코딩된 구성물이

MethodSpec - 제네릭 메서드의 구체 인스턴스화. Foo<string>()

StandAloneSig — 아무 선언에도 붙지 않은 독립 시그니처
주로 메서드의 지역 변수 목록과 calli의 호출 규약
