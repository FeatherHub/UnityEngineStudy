CPU 는 modified Harvard architecture


                         ┌─ ITLB ─ L1i ─┐
core / MMU ──────────────┤              ├─ L2 ─ L3 ─ DRAM
                         └─ DTLB ─ L1d ─┘
                         
L1i / L1d : 물리적으로 분리된 별도 SRAM 배열, 별도 포트, 별도 TLB(ITLB/DTLB)
L2 이하   : 통합. 명령어와 데이터가 같은 공간을 공유

---

명령어 fetch 는 L1d 를 건드리지 않는다

SoA 배열을 훑는 루프가 돌 때 명령어는 L1i 에서, 데이터는 L1d 에서 따로 온다. 
서로 evict 하지 않는다

---

명령어 쪽에는 L1i 앞에 한 겹이 더 있다
µop cache
타이트한 루프는 디코드된 µop 상태로 재생되기 때문에 L1i 조차 건드리지 않는다
SoA 순회 같은 전형적인 hot loop 는 명령어 측 메모리 트래픽이 사실상 0

Burst Length, 줄여서 BL

READ/WRITE 명령 한 번을 내린 뒤 연속해서 몇 번의 data transfer를 수행하는가

DRAM에 주소 X에서 1 byte만 주세요
식으로 매번 명령을 보내는 방식은 비효율적입니다.

한 번 읽기 시작했으면 주변 데이터를 연속으로 흘려보냅니다.
DDR5에서는 기본 burst length가 BL16으로 증가했습니다

---

cache line + set + way + tag

cache를 set-associative 구조로 구성
tag RAM과 data RAM을 별도로

Cortex-A73 L1 D-cache는 8-way 또는 16-way set associative
각 line에는 tag와 valid/coherency 상태가 함께 존재

---

set = 캐시 라인들을 묶어 놓은 그룹
associative = 그 그룹 안에서 tag를 비교해서 어느 line인지 찾아가는 방식

4-way set associative cache
하나의 set 에 4 개의 way ( cache line ) 

---

64 byte cache line
CPU가 0x1234 한 바이트를 읽어도 캐시는 그 주소가 들어 있는 64 B 덩어리를 가져옵니다.

주소
0x0000  ─┐
         │ 64 B   ← cache line 하나
0x003F  ─┘

0x0040  ─┐
         │ 64 B   ← 다음 cache line
0x007F  ─┘

---

32 KiB, 8-way, 64 B line

전체 용량 = 32 KiB
line 크기 = 64 B

32 KiB / 64 B
= 512 cache lines

8-way이므로

512 / 8
= 64 sets

이 데이터가 RAM 주소 어디에서 왔지?

그 답을 기록하는 것이 tag

---

private             같은 타입 안에서만
protected           같은 타입 + 파생 타입
internal            같은 assembly 안에서만
protected internal  protected 또는 internal        (합집합 — 더 넓다)
private protected   protected 그리고 internal      (교집합 — 더 좁다)
public              전부
file                같은 파일 안에서만  (C# 11+, source generator 용)
