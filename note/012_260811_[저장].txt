직렬화

씬·에셋·프리팹 저장/로드
Inspector — C# 프로퍼티를 호출하지 않고 직렬화 데이터를 직접 읽고 씁니다

---

직렬화 규칙

프로퍼티는 직렬화되지 않습니다
public 이거나 [SerializeField]
static / const / readonly 제외
커스텀 클래스·구조체는 [Serializable] 필요
다차원 배열, 배열의 배열, Dictionary, 중첩 컨테이너 불가

---

기본은 inline by value입니다.
커스텀 클래스를 참조가 아니라 값으로 host 객체 안에 펼쳐 넣습니다

---

null을 표현할 수 없음 → 빈 인스턴스로 대체됨
같은 객체를 두 필드가 가리켜도 저장 후엔 별개 객체 두 개
다형성 불가 → 부모 타입 필드에 자식을 넣으면 부모 필드만 저장되고 부모로 복원

저장 형식의 역사

초기 — 바이너리 + GUID/fileID

에셋 참조는 경로가 아니라 (GUID, fileID) 쌍입니다.
GUID 128비트는 .meta 파일에 들어 있어 "어떤 파일이냐",
fileID 64비트는 "그 파일 안의 어떤 객체냐"를 가리킵니다.

파일을 옮기거나 이름을 바꿔도 참조가 안 깨지는 이유
.meta를 버전 관리에서 빼면 프로젝트가 박살나는 이유

LZ = Lempel–Ziv
1977년 Abraham Lempel과 Jacob Ziv가 발표한 LZ77 계열 압축 알고리즘

LZ 계열은 이전에 등장한 바이트열을 찾아서 
“저 앞의 몇 바이트를 다시 복사해라” 같은 참조로 바꾸는 
사전(dictionary) 압축 계열

---

LZMA

초기 이름
Lempel
Ziv
Markov chain
Arithmetic coding

이후 arithmetic coding이 range coding으로 교체

Lempel–Ziv–Markov chain Algorithm

반복 데이터 탐색
      ↓
큰 dictionary를 적극 활용
      ↓
확률 모델 + range coding
      ↓
압축률을 높임

---

Unity AssetBundle에서는 
LZMA가 content section 전체를 하나의 연속 stream으로 압축합니다
압축률이 좋고 다운로드 크기를 줄이기에 유리

어떤 asset 하나를 읽을 때도 전체 압축 stream을 풀어야 하므로 random access 비용이 큽니다

Unity는 CDN으로 내려받는 AssetBundle에 LZMA를 적합한 선택으로 설명합니다

---

LZ4는 LZ77 계열이며 압축률보다는 압축/해제 속도에 강하게 최적화되어 있습니다

Serialization rules analyzer
유니티가 제공하는 Roslyn diagnostic analyzer
규칙 ID는 UAC1000부터 UAC1011까지.

UAC1001 — public 필드인데 그 타입에 [Serializable]이 없어 조용히 스킵됨

직렬화 제약

R1. 진짜 객체는 C++에 있다
Texture, Mesh, Transform은 C++ 객체
MonoBehaviour의 사용자 필드도 같은 파일, 같은 스키마 체계(TypeTree)에 들어가야 합니다

설계 목표는 "C# 언어의 표현력"이 아니라 **"C++ 멤버 레이아웃과 C# 클래스의 교집합"**

---

프로퍼티는 직렬화하지 않는다
C++ 쪽에 프로퍼티라는 개념이 없고 레이아웃은 필드 단위입니다.

TypeTree의 사용자 데이터 어휘가 "원시 타입, 고정 구조체, 동종 원소 배열 한 겹"으로 닫혀 있습니다

---

R2. 역직렬화는 런타임 예산 안에서 끝나야 한다

2005년 타깃은 모바일과 웹 플러그인

값 기반 인라인 저장이면 MonoBehaviour 하나의 데이터가 연속 블록이라 거의 그대로 읽어 들일 수 있습니다.
참조 registry는 id 조회와 개별 할당이 따라붙습니다

---

R3. 이 코드는 저장할 때만 도는 게 아니다

Instantiate 한 번이 직렬화 한 번입니다
도메인 리로드는 로드된 모든 MonoBehaviour를 직렬화합니다
초당 수천 번 도는 경로라, 순회 자체가 할당 없고 예측 가능해야 합니다

---

R4. Inspector가 직렬화 데이터만 보고 그려져야 한다

Inspector는 getter를 호출하지 않고 SerializedProperty로 직렬화 표현을 직접 읽고 씁니다
"직렬화되는 것 = 편집 가능한 것 = diff에 보이는 것"이 한 몸

역직렬화는 객체 그래프가 절반만 지어진 시점에 돕니다. 
참조가 아직 안 풀렸고 Awake도 안 불렸습니다. 
여기서 사용자 setter를 실행하면 그 코드가 아직 존재하지 않는 것들을 만지게 됩니다.

---

프로퍼티는 직렬화하지 않는다
SerializedProperty의 경로 문법이 표현할 수 있는 모양이어야 합니다
Inspector가 값을 쓰려면 주소 지정 가능한 저장 위치가 필요합니다

역직렬화 중에는 사용자 코드를 절대 실행하지 않는다는 원칙의 결과
ISerializationCallbackReceiver라는 명시적 훅이 따로 있는 이유

---

R5. 데이터가 코드보다 오래 산다

에셋은 사용자의 작업물이고 클래스 정의는 매일 바뀝니다

그래서 이름 기반 자기 서술 스키마, 없는 필드는 기본값, 모르는 필드는 무시, 
리네임은 FormerlySerializedAs

static은 인스턴스 데이터가 아니라 담을 슬롯이 없습니다.
const는 저장 위치 자체가 없습니다.

readonly는 역직렬화기가 네이티브 오프셋으로 직접 메모리를 쓰기 때문에, 쓸 수는 있지만

0층 — 인라인 값. 신원 없음. [Serializable] 커스텀 클래스의 기본. 두 필드가 같은 객체를 가리켜도 저장 후엔 별개
1층 — managed reference (rid). host 안에서만 유효
2층 — fileID. 파일 하나(씬, 프리팹, 에셋) 안에서 유효
3층 — GUID + fileID. 프로젝트 전역
