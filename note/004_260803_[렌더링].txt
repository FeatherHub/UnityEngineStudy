고정 경로 시대 (2005~2009, Unity 1~2)

렌더링 경로는 Vertex Lit / Forward 두 가지뿐
사용자는 ShaderLab으로 셰이더만 갈아끼웠죠

라이트 개수가 늘면 오브젝트를 라이트 수만큼 다시 그리는 multi-pass forward

---

Deferred의 도입 (2010, Unity 3.0)

Deferred Lighting(= Light Pre-Pass) 과 Illuminate Labs의 Beast 라이트맵퍼를 넣었습니다.
Deferred Shading이 아니라 Light Pre-Pass

당시 하드웨어에서 MRT 대역폭이 비쌌기 때문에 
G-buffer를 최대한 얇게(depth + normal + specular power) 유지하는 쪽을 택

대가는 지오메트리를 두 번 통과한다는 것
Base Pass(버퍼 채우기) → Lighting Pass(스크린 스페이스 라이팅) → Final Pass(다시 그리며 라이팅 합성)

---

PBR 대전환 (2015, Unity 5)

Standard Shader가 들어오면서 metallic/specular 워크플로우의 물리 기반 셰이딩이 기본이 되고, 
Enlighten 실시간 GI가 통합됐습니다

그리고 이 PBR 전환이 Light Pre-Pass를 죽였습니다
G-buffer가 얇으면 PBR에 필요한 정보(albedo, metallic, smoothness, occlusion)를 담을 수 없거든요

그래서 Deferred Shading으로 갈아타고
Light Pre-Pass는 "Legacy Deferred"로 강등

Standard 셰이더도 리플렉션 프로브도 지원 못 했으니까요

---

SRP, 렌더 루프를 C#으로 (2018, Unity 2018)

Unity가 렌더 루프 자체를 C#에 개방합니다. 
컬링, 드로우 순서, 패스 구성을 스크립트로 짜는 Scriptable Render Pipeline

동시에 두 개의 기성품 파이프라인
LWRP(모바일/저사양)와 HDRP(콘솔/PC 고사양) — 를 함께 냈습니다

같은 시기에 Shader Graph, Post Processing Stack v2, Progressive Lightmapper도 들어옵니다

---

ScriptableSingleton<T>

Editor state를 저장하는 generic class

직렬화된 데이터는 어셈블리 재로딩을 견디고 
[FilePath]를 사용하면 Unity 재시작 사이에도 유지된다

---

Unity가 스크립트를 다시 컴파일하고 
어셈블리 또는 도메인을 다시 로드하면 정적 필드는 초기화됩니다

에디터 도구가 가지고 있던 선택 상태, 검색 필터, 프로젝트 설정 등이 사라질 수 있습니다

---

1 instance에 처음 접근하면 CreateAndLoad()를 호출합니다.
2 [FilePath]가 있고 저장 파일이 존재하면 역직렬화합니다.
3 저장 파일이 없으면 CreateInstance<T>()로 ScriptableObject를 생성합니다.
4 도메인 재로드 중 ScriptableObject가 백업에서 복원되면 생성자가 다시 s_Instance를 연결합니다.
5 Save(bool)을 호출하면 지정된 파일에 현재 상태를 기록합니다.

[FilePath]가 없으면 Save()는 효과가 없습니다

Unity는 오픈소스 Mono 프로젝트의 자체 포크를 C# 스크립팅 런타임으로 사용합니다
MonoBehaviour의 네이티브 헤더 경로 Runtime/Mono/MonoBehaviour.h

현재는 IL2CPP로 빌드해도 여전히 MonoBehaviour를 사용합니다. 
즉 오늘날의 MonoBehaviour는 특정 빌드 백엔드를 요구한다기보다, 
역사적 이름이 유지된 C# 스크립트 Component 기반 클래스
