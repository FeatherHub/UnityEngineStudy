UnityEngine.Object 직렬화 시스템

직렬화 가능한 Object 그래프

---

UnityEngine.Object
├── GameObject          ← Scene에만 존재, Component의 컨테이너
├── Component
│   └── Behaviour
│       └── MonoBehaviour  ← GameObject에 종속, Scene/Prefab에 저장

---

UnityEngine.Object
└── ScriptableObject    ← GameObject 없이 독립 존재, .asset으로 저장
    ├── EditorWindow
    ├── Editor / PropertyDrawer
    ├── ScriptableSingleton<T>
    └── RenderPipelineAsset, InputActionAsset, VolumeProfile, ...
  
---

MonoBehaviour는 GameObject transform hierarchy에 매여 있고
ScriptableObject는 매여 있지 않다

그래서 SO는 Scene lifecycle이 아니라 Asset lifecycle을 따른다

---

세 개의 하위 시스템에 동시에 걸쳐 있다

Serialization — Unity의 YAML serializer
필드 선언만으로 저장·복원이 된다

---

Asset pipeline
asset 파일 하나 = SO 인스턴스 하나
AssetDatabase가 GUID + local file ID로 추적
이 참조가 build dependency graph를 형성

---

Editor UI

Inspector, Undo, multi-object edit, Prefab override diff가 
SerializedObject/SerializedProperty를 통해 따라온다

---

EditorWindow, 
custom Inspector, 
SRP asset, 
Input System asset, 
Timeline asset이 ScriptableObject 파생

---

Flyweight pattern
메모리 중복 제거

100개의 prefab이 동일한 밸런스 데이터를 각자 들고 있으면 100벌이 로드되지만, 
SO 하나를 참조하면 1벌만 로드된다

---

파생된 실용적 역할들

Configuration / balance data — 무기 스탯, 난이도 곡선 등
확장 가능한 열거형 — enum 대신 SO 인스턴스 자체를 identity로 쓴다
Pluggable behavior — SO에 virtual method를 두면 Strategy pattern이 된다

---

Scene 독립적 통신 채널

런타임 변수 공유, 
event channel

Singleton manager와 scene 간 결합을 걷어내는 용도

---

Serializer 우회

Unity serializer는 다형성 필드를 저장하지 못했다(SerializeReference 이전)
"다형적 데이터는 별도 SO asset으로 쪼갠다"

---

Godot

Resource를 상속한 스크립트를 만들면 .tres로 저장되고 Inspector에 노출된다
다만 Godot에서는 Texture, Mesh, Scene까지 전부 Resource

Unity는 native asset(Texture, Mesh)과 SO를 분리

---

Unreal — UDataAsset / UPrimaryDataAsset

UDataAsset : public UObject
"Create a simple asset that stores data related to a particular system"

UPrimaryDataAsset은 여기에 GetPrimaryAssetId()와 AssetBundle 지원을 얹어 
AssetManager가 수동 로드/언로드할 수 있게 한 버전으로, 
Unity의 Addressables 대응 축에 해당

---

CryEngine, Source 등 전통적 엔진은 
XML/config 파일 + 로더 코드 조합이라
object model이 없다

일반 프로그래밍 관점에서는 
JSON 설정 파일 + POCO에 (Plain Old C# Object)
에디터 통합과 참조 무결성을 얹은 것으로 볼 수 있다.

---

참조 무결성이 asset 단위로 보장

JSON/CSV 기반 데이터는 결국 문자열 ID나 경로로 참조된다
오타가 나거나 파일을 옮기면 런타임에야 깨진다

SO는 GUID + local file ID 기반의 UnityEngine.Object 참조라서
이름 변경·이동에 견디고
컴파일 타임에 타입이 검증되며

---

build dependency graph의 1급 시민이 된다

참조되지 않은 SO는 빌드에서 자동으로 빠지고
참조된 것은 자동으로 포함된다

---

UDataTable 행이나 JSON 객체는 순수 데이터다. 

SO는 asset이면서 동시에 virtual method dispatch의 대상이다. 
상속으로 asset 종류를 확장하고, 
디자이너가 파생 asset을 드래그해서 로직을 교체할 수 있다

---

함정

Play mode 변경이 asset에 남는다
에디터에서는 원본 asset이 수정되지만 
빌드에서는 로드된 복사본이 수정된다

---

domain reload와 얽힌 lifecycle

OnEnable/OnDisable 호출 시점이 
스크립트 리로드, 에디터 상태에 따라 달라져 직관에 반한다

---

참조의 전이적 로딩

SO가 prefab이나 texture를 참조하면 SO 로드 시 그것들도 함께 끌려온다

---

버전 관리 충돌

YAML 텍스트라 diff는 되지만, 
하나의 큰 SO를 여러 명이 편집하면 병합이 고통스럽다

---

에디터에는 "asset의 런타임 인스턴스"라는 개념이 없다

AssetDatabase는 GUID → instanceID → native object 포인터 매핑을 유지한다
어떤 asset이 한 번 로드되면 에디터 세션 동안 메모리에 인스턴스가 하나 존재하고
모든 참조가 그 하나를 가리킨다

Play mode 진입은 이 인스턴스를 복제하지 않는다
그래서 플레이 중 스크립트가 so.damage = 999를 하면 그건 asset 원본을 건드리는 것이다

---

Play mode 백업·복원 스냅샷은 Scene에만 적용된다

Play 진입 시 Unity는 열린 Scene을 메모리에 직렬화해 백업하고, 종료 시 그 백업으로 되돌린다
MonoBehaviour 필드 변경이 사라지는 이유가 이것

이 스냅샷 대상에 asset은 들어가지 않는다
프로젝트의 로드된 모든 asset을 매번 스냅샷 뜨는 건 비용상 비현실적이고

"플레이 중 Material 색을 조정하고 그 값을 유지한다"가 
Unity가 의도적으로 허용해온 authoring 워크플로다

---

(c) 빌드에는 write-back 경로가 없다.

빌드 시 참조된 asset들은 serialized file로 cook되어 build data에 복사된다
런타임은 그 복사본을 읽어 새 인스턴스를 만들고, 원본 .asset 파일은 빌드에 존재하지도 않는다

에디터와 빌드의 이 비대칭이 "에디터에서는 남고 빌드에서는 안 남는" 현상의 정체

---

필드에 대입해도 즉시 디스크에 쓰이진 않는다. 
native 값만 바뀌고, 파일 반영은 dirty 표시 이후 
Ctrl+S, AssetDatabase.SaveAssets, domain reload 직전, 에디터 종료 등의 시점에 일어난다. 

그래서 "가끔 남고 가끔 안 남는" 것처럼 보인다.

---

Instantiate(so)로 명시적 복제본을 만들어 쓰거나
SO를 read-only 규약으로 못박고 가변 상태는 별도 런타임 객체에 두거나
런타임 전용 필드에 [System.NonSerialized]를 붙인다

---

System.Object
└── UnityEngine.Object          ← native C++ 객체의 얇은 managed wrapper
    ├── GameObject
    ├── Component
    │   └── Behaviour
    │       └── MonoBehaviour
    ├── Material / Texture / Mesh / Shader / AnimationClip / ...   (native, 봉인됨)

---

System.Object
└── UnityEngine.Object          
    └── ScriptableObject
        ├── EditorWindow
        ├── Editor / PropertyDrawer / AssetPostprocessor 계열
        ├── ScriptableSingleton<T>
        └── RenderPipelineAsset, InputActionAsset, VolumeProfile, TimelineAsset, ...

---

UnityEngine.Object

instanceID, native counterpart와의 1:1 대응,
hideFlags(저장·파괴·가시성 제어)
Instantiate/Destroy/DontDestroyOnLoad
다른 Object의 직렬화 필드가 자신을 참조할 수 있는 자격

---

ScriptableObject

CreateInstance<T>() — native 객체를 먼저 만들고 managed wrapper를 붙이는 팩토리
new가 금지되는 이유가 이것이다.

메시지 콜백: Awake, OnEnable, OnDisable, OnDestroy, OnValidate, Reset
Update 계열은 없다 — player loop에 등록되지 않기 때문

[CreateAssetMenu]와 기본 Inspector 렌더링

---

Material/Texture/Mesh: GameObject 불필요, 그러나 native 봉인
사용자가 상속·필드 추가 불가

MonoBehaviour: C#으로 자유롭게 정의 가능
그러나 GameObject 종속

ScriptableObject: C#으로 정의 가능 × GameObject 불필요
A class you can derive from if you want to create objects that live independently of GameObjects

---

즉 UnityEngine.Object 계층은 원래 엔진이 닫아둔 native 타입 집합이었다
MonoBehaviour가 그 벽에 첫 구멍을 냈지만 GameObject라는 조건이 붙었고
ScriptableObject가 조건 없는 두 번째 구멍을 냈다

---

Unity에서 asset이란

AssetDatabase가 GUID를 부여해 추적하는 프로젝트 내 파일
그리고 그 파일을 import해서 얻어지는 UnityEngine.Object들

---

Source file — Assets/ 또는 Packages/ 아래의 실제 파일 (.png, .fbx, .cs, .asset, .unity, .prefab, .mat)

.meta file — GUID와 importer 설정을 담는다. 정체성은 경로가 아니라 GUID다
파일을 옮기거나 이름을 바꿔도 참조가 유지되는 근거가 이것이다.

Import artifact — Library/ 아래에 캐시된 native 표현
런타임에 실제로 로드되는 건 이쪽이다

---

참조의 표현은 GUID 단독이 아니라 (GUID, localFileID) 쌍이다
하나의 파일이 여러 Object를 담을 수 있기 때문

FBX 하나가 Mesh와 Material, AnimationClip, Avatar를 동시에 낳는다

---

main asset과 sub-asset이 각자 파일 내 local ID를 갖고
TryGetGUIDAndLocalFileIdentifier가 이 쌍을 다룬다.

직렬화된 필드에서는 {fileID: ..., guid: ..., type: ...} 형태로 보인다

---

"asset = 파일"이 아니다. 파일과 Object는 1:N이다
SO는 이 둘이 대체로 1:1이라 구분이 흐려질 뿐

.cs 스크립트도 asset이다
MonoScript object로 import된다
MonoBehaviour 컴포넌트는 직렬화될 때 자기 스크립트를 GUID로 참조

---

Resources/, StreamingAssets/, Addressables는 asset의 종류가 아니다
빌드 포함 규칙과 런타임 로드 경로의 차이일 뿐

기본 규칙은 "Scene에서 출발한 참조 그래프상 도달 가능한 것만 빌드에 포함"이고,
Resources/는 무조건 포함이라는 예외

---

모든 UnityEngine.Object는 세 상태 중 하나에 있다

Asset 파일 소유 — EditorUtility.IsPersistent가 true

Scene 소유 — Scene이 언로드되면 파괴된다
Scene의 GameObject는 IsPersistent가 false

무소속 — CreateInstance, new Material() 등으로 만든 것.

---

이분법이 깨지는 사례들

Scene 파일 안에 저장되는 ScriptableObject
MonoBehaviour 필드가 CreateInstance로 만든 SO를 참조하면, 
그 SO는 .asset 파일이 아니라 Scene 파일 안에 직렬화된다

Sub-asset으로서의 SO
AddObjectToAsset으로 다른 asset 내부에 SO를 심을 수 있다
AnimatorController의 state machine과 layer
Timeline의 track
파일 하나에 SO 수십 개가 들어있다.

---

Unity 직렬화는 기본적으로 tree를 쓴다. graph가 아니다

[Serializable] POCO 필드 → 값으로, 인라인 전개되어, 소유자 파일 안에 기록
UnityEngine.Object 참조 필드 → 포인터로 기록

정체성(identity)과 참조 가능성

---

POCO

공유가 불가능
두 MonoBehaviour가 같은 POCO 인스턴스를 참조하도록 코드로 만들어도, 
직렬화 시점에 각자 자기 복사본으로 써진다

로드하면 서로 다른 두 인스턴스가 된다
aliasing이 저장을 통과하지 못한다
POCO는 사실상 값 타입처럼 행동한다

---

null이 존재하지 않는다. POCO 필드가 null이면 serializer가 기본 생성된 인스턴스를 대신 쓴다
참조 의미론 자체가 없다는 뜻

---

다형성이 소실된다

Weapon 타입 필드에 Sword를 넣어도 선언 타입의 필드만 기록된다

---

SO

값 의미론에서 참조 의미론으로
UnityEngine.Object 참조는 Unity 직렬화에서 tree를 graph로 만드는 유일한 간선이고
SO는 그 간선의 목적지를 사용자가 정의할 수 있게 뚫어준 구멍이다

---

[SerializeReference]가 이 격차의 절반을 메웠다 (2019.3+)

POCO에 참조 의미론, 다형성, null, 순환 참조를 준다
하지만 그 참조는 한 파일 안에서만 유효하다

managed reference registry가 그 파일 하단에 붙고 파일 경계를 넘지 못한다

---

파일을 직렬화할 때 root object부터 필드를 순회하면서

값 타입 / [Serializable] 클래스 → 인라인 전개하고 재귀 계속
UnityEngine.Object 참조 → 거기서 순회를 멈추고 포인터만 기록

---

절단선은 "UnityEngine.Object 참조"

Object가 아닌 경로로 도달하는 모든 것은 파일에 녹아들고
Object 참조로 도달하는 것은 링크가 된다

같은 파일 안 → {fileID: <localID>}
다른 파일 → {fileID: <상대 파일 내 localID>, guid: <상대 파일의 GUID>, type: <2 등>}
null 또는 유실 → {fileID: 0}

---

절단선이 결정하는 실무적 결과

로드 granularity — 파일을 로드하면 인라인된 내용은 전부 오고, 외부 참조는 전이적으로 끌려온다
SO 하나가 prefab을 참조하면 절단선 너머가 통째로 딸려온다.

참조 안정성 — 경계를 넘는 참조만 GUID를 쓰므로 파일 이동·리네임에 강하다
파일 내부 참조는 localFileID뿐이라 파일을 쪼개면 깨진다.

GUID + importer 설정 + importer별 데이터
이게 없으면 asset이 아니다.

---

엔진 쪽에서 본 정의 — 역할 없는 UnityEngine.Object

Material = 엔진 객체 + 셰이더를 파라미터화하는 일
Mesh = 엔진 객체 + 지오메트리를 담는 일
MonoBehaviour = 엔진 객체 + GameObject에 붙어 프레임 콜백을 받는 일

---

ScriptableObject = 엔진 객체 + (일 없음).
역할이 지정되지 않은 UnityEngine.Object

왜 EditorWindow가 이걸 상속하나
에디터 창은 엔진 객체 자격(domain reload를 넘는 직렬화)은 필요했지만 엔진 역할은 없었다

주소를 가질 수 있는 C# 객체

평범한 C# 객체는 프로세스 안에서만 정체성을 갖는다
직렬화하는 순간 정체성은 사라지고 구조만 남는다

Unity는 자기 에셋들을 위해 파일 경계를 넘고 세션을 넘어 유지되는 
주소 체계 (GUID, localFileID)를 만들었다. 
ScriptableObject는 "사용자도 이 주소를 발급받을 수 있다"고 선언한 지점이다

---

주소가 있다 → 여러 곳에서 같은 하나를 가리킬 수 있다 → 공유, Flyweight
주소가 있다 → 독립적으로 로드·언로드 가능 → AssetBundle, Addressables
주소가 있다 → 단독으로 열어 편집 가능 → Inspector target, Undo, .meta
주소가 있다 → 의존성 그래프의 노드 → 빌드 포함 결정

---

눈에 보이는 참조는 "Theme → Tile 15개" 하나뿐이지만, 
진짜 참조자는 Tilemap의 셀 배열이다.

Tilemap은 셀마다 TileBase 참조를 하나씩 저장한다
Expert 보드가 30×16이면 480개 셀, 480개의 참조가 15개 객체로 수렴한다
Flyweight

---

공유 — N개가 같은 하나를 가리켜야 한다 (N → 1)
교체 — 하나의 슬롯이 N개 후보 중 하나를 가리켜야 한다 (1 → N)

---

값이면 POCO — 데이터가 그 자리에 있는 것이다. 
SO — 데이터는 어딘가에 있고 필드는 그중 하나를 가리킬 뿐이다

---

ClassicTheme과 DarkTheme은 "테마 필드가 가질 수 있는 값 두 개"가 아니라 두 개의 독립적 대안이다
세 번째 테마를 추가할 때 코드가 한 줄도 안 바뀐다는 게 주소의 값어치다.
런타임 테마 전환도 참조 하나 갈아끼우면 끝
