XLIFF
XML Localization Interchange File Format

OASIS 표준(1.2 / 2.0)
번역 회사와 주고받는 교환 포맷

단순 key-value(CSV)와 다른 점은 번역 워크플로 자체를 담는다는 것

<source> 원문과 <target> 번역문이 한 unit 안에 쌍으로 존재
state 속성으로 상태 추적 — new, translated, reviewed, final
<note> 로 번역가에게 줄 문맥 설명 첨부
원문이 바뀌면 해당 unit만 상태가 되돌아가 재번역 대상이 드러남

Newtonsoft.Json
com.unity.nuget.newtonsoft-json

NET 생태계의 사실상 표준 JSON 라이브러리
Json.NET을, Unity가 UPM 패키지로 재배포한 것

Unity 내장 JsonUtility가 있는데도 의존하는 이유는 JsonUtility의 제약 때문

다형성(polymorphic) 직렬화 불가 — 인터페이스·추상 클래스 필드 처리 못 함
Dictionary 미지원
최상위 배열 미지원
null 처리와 커스텀 converter 부재

---

JsonUtility는 C# 리플렉션이 아니라 
Unity의 네이티브 직렬화기(Inspector가 쓰는)를 그대로 호출합니다

속도와 GC — 단순 DTO 기준으로 Json.NET보다 빠르고 할당이 적음
매 프레임 오가는 데이터라면 유의미한 차이

Unity 타입이 그냥 됨
Newtonsoft로 Vector3를 던지면 normalized, magnitude 같은 property까지 타고 들어가 
재귀에 빠지므로 custom converter가 필수

FromJsonOverwrite
기존 인스턴스에 덮어쓰기. 객체 재사용이 가능하고, 
MonoBehaviour·ScriptableObject 인스턴스에도 적용됨.

[SerializeField] private 필드를 그대로 인식

빌드 부담 없음 — 추가 DLL 없고, 네이티브라

---

Newtonsoft가 필요해지는 지점

Dictionary, 최상위 배열, null 구분, interface·추상 클래스 다형성
남이 만든 API 응답 파싱 — 필드명 규칙(snake_case)이 다르거나 스키마가 유동적일 때
파싱 실패 시 예외와 메시지가 필요할 때. JsonUtility는 타입이 안 맞아도 조용히 기본값을 넣고 넘어감
부분 파싱, JObject로 훑기, custom converter, [JsonIgnore] 같은 세밀한 제어

---

원본은 James Newton-King의 Json.NET(NuGet Newtonsoft.Json)
com.unity.nuget.newtonsoft-json 3.2.2가 Json.NET 13.0.2에 동기화되어 있습니다

DLL이 두 벌

Runtime/Newtonsoft.Json.dll(Mono/Editor용)
Runtime/AOT/Newtonsoft.Json.dll

AOT 빌드는 System.Reflection.Emit 기반 동적 IL 생성을 제거한 버전

CAT
Computer-Assisted Translation

Trados, memoQ, Crowdin

Translation Memory, TM: 이전 번역을 저장하고 비슷한 문장이 나오면 재사용 후보를 제시

QA: 숫자 누락, 태그 손상, 용어 불일치 같은 문제를 검사합니다
XLIFF 같은 교환 포맷 지원: 개발팀과 번역팀 사이에서 문자열과 메타데이터를 주고받습니다

com.unity.localization

SharedTableData가 각 엔트리에 내부 숫자 ID를 부여하고
TableReference와 TableEntryReference는 이름 대신 그 ID를 참조합니다
그래서 키 이름을 리팩터링해도 참조가 끊기지 않습니다.

I2, Lean, gettext 계열이 전부 문자열 키를 그대로 참조하기 때문에 겪는 고질병
키 오타 하나, 이름 정리 한 번에 참조가 조용히 죽는 문제를 구조적으로 없앴습니다

문법 로직을 코드에서 데이터로 밀어낸 것

Smart Strings 이전의 관행은 "You have " + n + " items" 였고
이건 영어 외의 언어에서 무조건 깨집니다

로컬라이제이션을 "텍스트 교체"가 아니라 "프로퍼티 variant"로 재정의한 것

독일어에서 버튼이 터지는 문제, 아랍어에서 앵커를 뒤집어야 하는 문제, CJK에서 폰트 크기를 올려야 하는 문제는 
전부 텍스트가 아니라 레이아웃 문제인데, 
기존 솔루션들은 이걸 prefab variant 복제로 해결하라고 했습니다. 
Unity는 컴포넌트 프로퍼티 단위 diff로 풀었습니다.

---

SharedTableData
responsible for the localization keys and associating the keys to unique ids
컬렉션 하나당 하나 존재

ScriptableObject

public class SharedTableEntry
{
    public long Id { get; }                     // 고유 ID, 절대 안 바뀜
    public string Key { get; }                  // 사람이 읽는 이름, 바뀔 수 있음
    public MetadataCollection Metadata { get; } // 번역가 주석 등
}

Key와 Id를 분리한 것이 이 패키지의 핵심 설계
START_GAME을 MENU_START로 바꿔도 모든 참조가 살아남습니다

---

Id

Sequence 12bit — 같은 밀리초 내 로컬 카운터. 밀리초당 4095개까지
Machine Id 10bit — 에디터에서는 네트워크 인터페이스 물리 주소로 생성. 1024대까지
Epoch Timestamp 41bit — 커스텀 epoch 기준. 69년치

여러 명이 동시에 같은 테이블에 키를 추가해도 ID가 충돌하지 않습니다

StringTable — 한 언어의 값을 담는 곳

LocalizationTable을 상속한 ScriptableObject
Locale 하나당 하나

LocaleIdentifier를 들고 있고 SharedData 참조를 통해 키 정의에 접근합니다

public class StringTableEntry : TableEntry
{
    public string Value { get; }      // 포맷 적용 전 원본 문자열
    public bool IsSmart { get; }      // Smart String 여부
    public FormatCache FormatCache { get; } // 파싱 결과 캐시
}

IsSmart가 true면 SmartFormat이, false면 string.Format이 돌아갑니다

StringTableCollection

UnityEditor.Localization 네임스페이스
에디터 전용이고 빌드에 포함되지 않습니다

행 = 키 → SharedTableData가 정의
열 = 언어 → StringTable 하나가 열 하나
컬렉션 = 그 표를 표처럼 보여주는 뷰

LocalizationSettings
프로젝트당 하나인 ScriptableObject

전체 시스템의 서비스 로케이터
모든 조회가 결국 여기를 거칩니다

---

InitializationOperation
AsyncOperationHandle<LocalizationSettings>
부팅 시 반드시 대기해야 합니다
이걸 안 기다리고 AvailableLocales를 읽으면 빈 목록이 나옵니다

AvailableLocales — ILocalesProvider. 사용 가능한 언어 목록
SelectedLocale / SelectedLocaleAsync / SelectedLocaleChanged — 현재 언어와 변경 이벤트

SelectedLocale에 대입하는 순간 전역 이벤트가 퍼지고 
살아 있는 모든 LocalizedString이 갱신됩니다. 
언어 전환의 공식 경로

---

// 나쁨 - 이름 기반. 테이블명이나 키명 변경 시 런타임에 조용히 실패
var s = new LocalizedString("UI Text", "START_GAME");

// 좋음 - 인스펙터에서 지정. GUID + Id로 직렬화된다
[SerializeField] LocalizedString startGame;

초기화를 기다리지 않으면 AvailableLocales가 비어 있습니다.

public class Bootstrap : MonoBehaviour
{
    // Bootstrap::Start - 로컬라이제이션 초기화(로케일 로드 + preload) 완료를 대기
    IEnumerator Start()
    {
        yield return LocalizationSettings.InitializationOperation;

        // 이 시점부터 SelectedLocale, AvailableLocales가 유효하다
        SceneManager.LoadScene("MainMenu");
    }
}

---

오디오에서 중앙 카탈로그를 경계했던 가장 큰 이유

그 매니저 프리팹이 게임의 모든 오디오를 참조하는 순간, 첫 씬 로드에서 전부 메모리에 올라간다

로컬라이제이션에는 이 문제가 없습니다. 
LocalizedString은 테이블 GUID와 Key Id만 들고 있는 구조체일 뿐, AudioClip 같은 실제 에셋 참조가 아닙니다

필드가 1000개여도 카탈로그 자체는 수십 KB이고, 
실제 로딩은 Addressables가 테이블 단위로 따로 합니다.

소유자가 있는 텍스트 → 분산

아이템 이름, 몬스터 설명, 스킬 툴팁, 특정 UI 화면의 라벨.

public class ItemDefinition : ScriptableObject
{
    [SerializeField] LocalizedString displayName;
    [SerializeField] LocalizedString description;
}
