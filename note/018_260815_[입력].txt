PreLateUpdate 안에 ScriptRunBehaviourLateUpdate가 들어 있다
"LateUpdate 이전" phase가 LateUpdate를 실행한다.

Initialization은 매 프레임 돈다. 초기화가 아니다

PostLateUpdate는 실질적으로 렌더/프레젠트 phase다. 
정의된 노드가 40개를 넘어 전체에서 가장 뚱뚱한데, 이름에 렌더는 한 글자도 없다.

반대로 Update에는 노드가 4개뿐이다. 
사용자가 "메인"이라고 믿는 phase가 실제로는 가장 얇다

EarlyUpdate와 PreUpdate는 이름만으로 구분할 방법이 없다

InputEndFrame은 그 프레임의 모든 독자가 읽고 난 뒤라야 엣지 플래그를 지울 수 있으니 맨 뒤다.

접두사 명명이 구조적으로 막다른 길인 이유

이름 공간에 순서를 인코딩하면 삽입할 때마다 새 이름을 요구한다

리스트는 실제보다 강한 순서를 강제한다
진짜 제약이 "A 뒤, B 앞"이면 그 사이 어디든 되는데, 리스트는 한 자리를 고르게 만든다

---

이상적 루프

phase는 명사로 명명한다
Input, Simulate, Animate, Layout, Render, Present

순서는 선언적 제약 + 위상 정렬
제약이 없는 것들끼리는 결정론적 tiebreak로 고정한다

배리어를 1급 개념으로
"입력 확정", "트랜스폼 확정" 같은 지점에 이름을 준다
배리어 이름은 이유를 담고 있어서, 나중에 배리어가 옮겨져도 의미가 보존된다.

위치가 데이터 접근에서 유도돼야 한다
"이 시스템은 Transform을 쓰고 Velocity를 읽는다"만 선언하면 스케줄러가 read/write 충돌로 순서를 뽑아낸다

---

frame
├ Timing                프레임 페이싱, 시계 전진
├ Input                 디바이스 → 이벤트 버퍼
│   ══ barrier: InputFrozen        이 프레임의 입력 확정
├ Simulate
│   ├ FixedStep × n     입력 소비 → 게임 로직 → 물리 적분
│   └ VariableRate      고정 스텝이 불필요한 로직
│   ══ barrier: WorldSettled       월드 상태 확정
├ Animate               애니메이션 → 스키닝 → IK → 카메라
│   ══ barrier: TransformsFinal    트랜스폼 확정
├ Layout                UI 레이아웃, 컬링
├ Render                늦은 입력 재샘플링(XR 포즈) → 드로우
└ Present

각 박스 안쪽은 리스트가 아니라 DAG다
새 시스템을 넣을 때 하는 일은 이름을 발명하는 게 아니라 
after(InputFrozen) 같은 제약을 붙이는 것이다

대가

위상 정렬은 한눈에 안 보인다
리스트는 그냥 읽으면 되지만 DAG는 도구가 있어야 이해된다

제약이 없는 시스템끼리의 순서가 미정이라는 것도 비용이다
결정론을 위해 인위적 tiebreak를 넣으면, 사람들은 곧 그 tiebreak에 의존하기 시작한다

중재 아키텍처

Arena — 포인터별 경쟁 (Flutter)

arena의 키는 포인터 id
그 포인터에 히트된 recognizer들이 전부 arena에 들어가 경쟁한다
The first member to accept, or the last member to not reject, wins

add(열림) → close(down 디스패치가 끝나면 신규 참가 차단) → 해소 → sweep(up 시점에 강제 해소)

eagerWinner — arena가 아직 열려 있는데 누군가 승리를 선언하면 즉시 확정하지 않고 보류했다가 close 시점에 적용한다
아직 등록도 안 된 참가자를 선점해버리는 걸 막는다

sweep — up이 왔는데 아무도 승리를 주장하지 않으면 리스트 첫 번째가 자동으로 이긴다
수동적인 recognizer들끼리 교착에 빠져 사용자가 아무것도 못 하게 되는 상황의 방지책

hold / release
sweep을 넘겨서까지 살아 있어야 하는 recognizer
(더블탭이 대표적이다. 첫 탭이 끝나도 두 번째 탭을 기다려야 한다)가 arena를 붙잡아 둔다

public sealed class GestureInterpreter
{
    // ── 이벤트 (화면 좌표만. 셀도 카메라도 모른다)
    public event Action<Vector2> Tapped;              // screenPos
    public event Action<Vector2> SecondaryTapped;     // PC 우클릭 전용
    public event Action PanBegan;
    public event Action<Vector2, Vector2> Panned;     // prevPos, currPos
    public event Action PanEnded;
    public event Action<float, Vector2> Zoomed;       // scaleFactor, pivotPos
    public event Action Cancelled;

    // ── 상태 (디버그 HUD용 읽기 전용)
    public GesturePhase Phase { get; private set; }

    // ── 필드
    GestureThresholds _t;
    int _primaryId, _secondaryId;
    Vector2 _pressPosition;        // 임계 판정 기준점
    Vector2 _lastPosition;         // 팬 델타 계산용 직전 위치
    Vector2 _releasePosition;      // 탭 확정용. 손가락이 사라진 뒤에도 유효
    float _pressElapsed;           // 롱프레스 대비. 지금은 기록만
    float _lastPinchDistance;

    public GestureInterpreter(in GestureThresholds t);

    // GestureInterpreter::Tick — 프레임당 한 번. 유일한 진입점
    public void Tick(in PointerFrame frame, float deltaTime);

    // GestureInterpreter::Reset — 포커스 상실, 회전, 씬 전환
    public void Reset();

    // GestureInterpreter::UpdateThresholds — 화면 회전으로 dpi 기준이 바뀔 때
    public void UpdateThresholds(in GestureThresholds t);
}

---

Tick의 전이

GainedFirst          → PressPending. pressPosition·lastPosition 기록, pressElapsed = 0

PressPending
  ├ 이동 > TapMovePx → Panning. PanBegan, Panned(pressPosition, curr)
  ├ GainedSecond     → Pinching. 탭 후보를 조용히 폐기          
  └ LostAll          → Tapped(releasePosition), Idle

Panning
  ├ 이동             → Panned(lastPosition, curr)
  ├ GainedSecond     → Pinching. 기준 재설정, 이번 프레임은 무발행
  └ LostAll          → PanEnded, Idle

Pinching
  ├ 첫 프레임        → lastPinchDistance만 기록, 무발행           
  ├ 이후             → Panned(prevCentroid, currCentroid)
  │                    Zoomed(dist / lastPinchDistance, currCentroid)
  └ LostToOne        → Panning. 남은 손가락으로 lastPosition 재설정, 무발행 

어느 상태든
  ├ Scroll != 0      → Zoomed(pow(ZoomPerNotch, scroll), 커서 위치)
  ├ SecondaryPressed → SecondaryTapped(curr)
  └ FocusLost/Overflow → Reset() → 진행 중이었으면 Cancelled

// PointerReader::Read — 마우스든 터치든 PointerFrame 하나로 만든다
public PointerFrame Read()
{
    _buffer.Clear();
    var device   = PointerDevice.None;
    float scroll = 0f;
    bool secondary = false;

    // 1) 터치 먼저 본다
    var ts = Touchscreen.current;
    if (ts != null)
    {
        foreach (var t in ts.touches)
        {
            var phase = t.phase.ReadValue();
            if (phase == UnityEngine.InputSystem.TouchPhase.None) continue;

            _buffer.Add(new PointerSnapshot {
                Id       = t.touchId.ReadValue(),
                Position = t.position.ReadValue(),
                Phase    = MapPhase(phase)
            });
        }
        if (_buffer.Count > 0) device = PointerDevice.Touch;
    }

    // 2) 터치가 없을 때만 마우스
    if (device == PointerDevice.None && Mouse.current is { } m)
    {
        bool down = m.leftButton.wasPressedThisFrame;
        bool up   = m.leftButton.wasReleasedThisFrame;

        if (m.leftButton.isPressed || up)
        {
            _buffer.Add(new PointerSnapshot {
                Id       = MouseId,                       // 상수 0
                Position = m.position.ReadValue(),
                Phase    = down ? PointerPhase.Began
                         : up   ? PointerPhase.Ended
                                : PointerPhase.Moved
            });
        }
        scroll    = m.scroll.ReadValue().y;
        secondary = m.rightButton.wasPressedThisFrame;

        if (_buffer.Count > 0 || scroll != 0f || secondary)
            device = PointerDevice.Mouse;
    }

    var change = ComputeChange(_buffer.Count);   // _lastCount와 비교
    _lastCount = _buffer.Count;

    return new PointerFrame(device, _buffer, change, scroll, secondary, _focusLost);
}

void Update()

IdleState      → PointerMachine 안에
PendingState   → PointerMachine 안에
DraggingState  → PointerMachine 안에
PinchingState  → 상태가 아니라 머신이 됐다. PinchMachine

---

Idle / Pending / Dragging은 전부 **"이 포인터의 제스처"**가 어떤 상태냐를 말한다
그런데 Pinching은 **"두 포인터의 관계"**가 어떤 상태냐를 말한다

---

이전 GestureInterpreter는 세 가지 일을 하고 있었다

1. 한 제스처의 상태 머신을 돌린다        ← GestureState들을 구동
2. "손가락 두 개"가 무슨 뜻인지 정한다     ← PinchingState로 뭉뚱그려져 있던 것
3. 공개 이벤트 표면을 소유한다

셋을 분리하면 이렇게 된다.

1 → PointerMachine     (그리고 포인터마다 하나씩, N개)
2 → IGestureMode       (조립 + 중재)
3 → GestureRuntime     (이벤트 + 모드 전환)

---

GestureRuntime                 모드 스택 + 공개 이벤트 소유
      │
      ▼
IGestureMode                   현재 모드 하나만 동작
      ├── MultiDragMode        PointerMachine × N        (인게임, 협력 제스처 없음)
      └── NavigationMode       PointerMachine × 1        (메뉴, 지뢰찾기)
                               PinchMachine × 1

---

PointerMachine                 여기가 상태 머신
      └── GestureState         Idle / Pending / Dragging

PinchMachine                   상태 머신 아님. 관계 추적만

---

이 영역에는 확립된 용어가 있다

UIKit    UIGestureRecognizer
Flutter  GestureRecognizer
Fingers  GestureRecognizer

PointerMachine   →  PointerRecognizer     포인터 하나에서 탭/드래그를 인식
PinchMachine     →  PinchRecognizer       포인터 둘에서 핀치를 인식
GestureRuntime   →  GestureSystem         모드 스택 + 이벤트 소유
IGestureMode                              그대로. 언리얼의 InputMode와 같은 어휘

---

PointerRecognizer가 탭과 드래그를 둘 다 인식하는 건 UIKit과 다른 점
UIKit은 UITapGestureRecognizer와 UIPanGestureRecognizer를 따로 두고 서로 경쟁시킨다

---

초기화    내 데이터를 세운다        → 생성자가 대체한다. 이건 맞았다
통지      내가 시작/종료됐음을 알린다  → 생성자로 대체할 수 없다

---

TwoFingerRecognizer는 한 곳이 걸린다 — 마우스에는 손가락이 없다
우리 어휘가 PointerFrame, PointerSnapshot으로 통일돼 있으니 TwoPointerRecognizer가 일관된다

PointerRecognizer(1개)와 TwoPointerRecognizer(2개)가 짝이 된다

---

WinRT가 translate/scale/rotate 묶음을 manipulation이라 부르고
TouchScript도 TransformGesture로 셋을 합쳐 놨다

ManipulationRecognizer

---

탭                   칸 열기 / 깃발
한 손가락 드래그     카메라 팬
두 손가락            핀치 (줌 + 팬)
마우스               클릭, 드래그, 휠, 우클릭

---

한 손가락 드래그   대상을 옮긴다
두 손가락 드래그   화면을 옮긴다

---

UIKit        view.addGestureRecognizer(pinch);  pinch.addTarget(self, action:)
TouchScript  각 Gesture 컴포넌트가 자기 StateChanged를 갖는다
Fingers      각 GestureRecognizer가 자기 콜백을 갖는다

전부 소비자가 특정 recognizer를 지목해서 구독한다
합칠지는 소비자가 정해야 하고, recognizer는 늘었다 줄었다 해야 하니까

---

GestureSystem            recognizer 소유, 프레임 배분, 중재(absorb/handoff), 모드 전환
                         이벤트를 갖지 않는다

PointerRecognizer        public event Tapped, DragBegan, Dragged, DragEnded
ManipulationRecognizer   public event Began, Dragged, Scaled, Rotated, Ended

---

// GameBootstrap::Awake
void Awake()
{
    var thresholds = _settings.Resolve(Screen.dpi);

    _reader        = new PointerReader();
    _pointer       = new PointerRecognizer(thresholds);
    _manipulation  = new ManipulationRecognizer(thresholds);

    _system = new GestureSystem();
    _system.Add(_pointer);
    _system.Add(_manipulation);

    _picker  = new CellPicker(_camera, _grid);
    _session = new GameSession(new Board(...));

    // ── 배선. 무엇을 같은 의미로 볼지가 여기서 결정된다
    _pointer.Tapped       += p => { if (_picker.TryPick(p, out var c)) _session.TapCell(c); };
    _pointer.Dragged      += _cameraRig.HandlePan;
    _manipulation.Dragged += _cameraRig.HandlePan;      // 두 손가락 팬도 같은 의미로
    _manipulation.Scaled  += _cameraRig.HandleZoom;
    // _manipulation.Rotated 는 구독하지 않는다 = 회전 비활성

    _session.CellsChanged += _boardView.Apply;
    _session.GameEnded    += _hud.ShowResult;
}
