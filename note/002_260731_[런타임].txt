IL2CPP

C# 의미론을 C++ 문법으로 부호화한 기계 생성물

C#의 arr[i] = x;

if (arr == NULL) raise(Exception::GetNullReferenceException(...));   // null 검사
if (i >= arr->max_length) raise(Exception::GetIndexOutOfRangeException()); // 경계 검사
arr->vector[i] = x;

C# 컴파일러는 IL에서 멈춥니다.

모든 일을 바깥에서

---

IDE가 에디터 프로세스 안의 Mono VM에 디버거 프로토콜로 붙는 것
디버거 서버가 프로세스 안에 산다

managed 디버깅은 구조가 반대
런타임 자신이 디버그 에이전트 — 즉 서버를 내장

Unity 에디터의 Mono VM은 로컬 TCP 소켓을 열어놓고 기다리고, 
에디터는 자기 프로세스 정보를 프로젝트의 Library/EditorInstance.json에 광고

IDE의 "Attach to Unity"는 그걸 읽어 TCP로 접속하는 클라이언트일 뿐
접속 후엔 와이어 프로토콜로 대화

"이 메서드의 이 IL 오프셋에 브레이크포인트", "스텝", "이 지역변수 값 줘". 

브레이크포인트에 걸리면 VM이 스스로 안에서 managed 스레드들을 멈추고 클라이언트에 통지
JIT가 코드를 만들 때 IL↔소스 줄 매핑(sequence point)을 심어두었기에 가능한 일

---

코어가 네트워킹을 소유하지 않은 탓에 서드파티 생태계(Mirror, Fish-Net, Photon)가 크고, 
실전에서는 NGO 대신 이쪽을 쓰는 팀도 많습니다

Burst 컴파일

C#의 제한된 서브셋(HPC# — managed 객체 없음, GC 할당 없음, blittable 값 타입만)을 받아서,
LLVM(Clang과 같은 최적화 백엔드)으로 컴파일하는 Unity 전용 컴파일러

[BurstCompile]을 붙인 잡(IJob류)이나 ISystem이 대상 
에디터에선 백그라운드로, 플레이어 빌드에선 AOT로 미리 컴파일

---

NativeContainer들은 서로 겹치지 않음(noalias)이 보장돼서 
C++ 컴파일러가 못 하는 벡터화가 합법이 되고, 

Unity.Mathematics의 float4 같은 타입은 SIMD 레지스터에 직결되고, 
안전검사는 에디터에선 유지·빌드에선 제거되며, 
타깃 CPU(AVX2 등)별 코드를 뽑습니다

그 영역 안에서만 클래스·GC·리플렉션을 포기하고, 대신 최상급 codegen을 받는 거래

---

C# 소스 → IL(컴파일러 = Roslyn), 
후반전: IL → 기계어(런타임의 JIT). 

"codegen 품질"은 후반전 실력

같은 IL을 받아도 JIT마다 만드는 기계어가 다릅니다

인라인을 얼마나 과감히 하나, 
struct를 레지스터에 유지하나 메모리에 흘리나, 
루프에서 경계 검사를 증명해 제거하나, 자동 벡터화를 하나

---

Microsoft의 런타임은 .NET Core로 재출발하면서 RyuJIT라는 새 JIT를 얻었고, 
이후 십 년간 계층형 컴파일, PGO(실행 프로파일 기반 재최적화), 벡터화 등 투자가 집중

반면 Mono는 2001년생 프로젝트로, MS가 인수한 뒤 투자 축이 .NET로 쏠리며 사실상 유지보수 모드

Unity는 그 Mono를 오래전에 포크했고(설치 폴더의 MonoBleedingEdge), 
자체 GC(Boehm)와 콘솔 포팅을 얹으며 갈라져 나와서 
.NET의 발전을 따라 당길 수 없는 상태

---

"처진다"의 실체

같은 C# 코드가 Unity Mono 위에서 현대 .NET 위에서보다 느립니다
핫루프에선 수 배까지 벌어질 수 있습니다. 

인라인 휴리스틱이 소극적이고, struct가 자주 스택에 흘려지고, 
경계 검사 제거가 약하고, 벡터화가 없다시피

전반전은 낡지 않았습니다.

---

Roslyn

Microsoft의 오픈소스 C# 컴파일러 플랫폼

컴파일의 전 과정(구문 트리, 의미 모델, 심볼)을 API로 노출하는 라이브러리

IDE의 인텔리센스·리팩토링, analyzer(커스텀 컴파일 경고), source generator가 전부 같은 API 위에 지어집니다. 

에디터가 Roslyn을 내장해 스크립트를 직접 컴파일하고(IDE 빌드가 무의미했던 이유), 
NGO의 RPC 글루 코드나 DOTS의 ISystem 보일러플레이트가 source generator로 만들어집니다. 

---

HPC#
High Performance C#

C# 문법 그대로, 허용 범위만 좁힌 부분집합

Burst가 컴파일해주는 코드 안에서는 
class(참조 타입) 사용 금지, GC 할당 금지, 예외는 제한적, 
허용되는 건 값 타입과 NativeContainer들 — 그중에서도 blittable 타입

blittable이란 "managed 쪽과 네이티브 쪽의 메모리 표현이 동일해서 비트 그대로 복사 가능한 타입"
(int, float, 그것들로만 구성된 struct는 되고, string이나 class 참조는 안 됨)

---

공격적 컴파일 = 시간과 메모리를 아낌없이 태워서 최적화 패스를 깊게 도는 것
인라인을 몇 단계씩 파고들고, 루프를 펼치고, 벡터화를 시도하고, 레지스터 할당을 정교하게 푸는 것
컴파일 시간을 내주고 실행 속도를 사는 거래

---

JIT는 게임이 도는 중에 컴파일
메서드 하나에 LLVM급 최적화를 돌리면 수십~수백 배의 컴파일 시간이 들고, 
그 스톨이 프레임 드랍으로 직결

그래서 현대 .NET의 타협이 계층형 컴파일(일단 빠르게 대충 → 뜨거워진 메서드만 백그라운드에서 재최적화)

---

벡터화(SIMD)

CPU에는 한 명령으로 여러 데이터를 동시에 처리하는 명령어들
AVX2면 float 8개를 한 번에 곱하고 더합니다. 

자동 벡터화란 컴파일러가 스칼라 루프(한 번에 하나)를 이런 SIMD 루프(한 번에 8개)로 변환하는 것
이론상 8배

---

aliasing

두 포인터가 겹치는 메모리를 가리키는 상황
벡터화를 죽인다
C++ 컴파일러는 임의의 두 float*가 안 겹친다는 걸 증명할 방법이 없습니다

---

6.5에서 새 런타임 세션의 생명주기 API 도입
6.6에서 Fast Enter Play Mode 기본화
6.7 LTS에서 실험적 CoreCLR 데스크톱 플레이어
6.8에서 Mono  은퇴 .NET 10 + C# 14 탑재

---

Boehm은 객체를 안 옮기는 GC라 m_CachedPtr 같은 날 포인터 상호참조가 성립했는데, 
CoreCLR의 GC는 객체를 이동·압축합니다. 

네이티브↔managed 래퍼 아키텍처 전체가 "객체는 제자리에 있다"는 가정 위에 있었으니 근본 수술이 필요

---

도메인 리로드는 AppDomain unload 위에 지어졌는데 
CoreCLR엔 AppDomain이 없습니다(대체물인 AssemblyLoadContext는 강제 언로드가 안 됨)

---

.NET(Mono 세대)에 AppDomain 

프로세스 안의 프로세스 같은 격리 단위
로드된 어셈블리들, static 변수들, JIT 산출물이 이 안에 삽니다

Mono에선 어셈블리 하나만 콕 집어 언로드할 수 없습니다
낡은 코드를 치우는 유일한 방법이 도메인을 통째로 내리는 것

Unity의 스크립트 갱신 절차

에디터 상태를 직렬화로 백업 
→ 도메인 언로드(모든 managed 객체·static·이벤트 구독·JIT 코드 소멸) 
→ 새 도메인 생성 
→ 새 어셈블리 로드 
→ 초기화 재실행(EditorAssemblies::ProcessInitializeOnLoadAttributes의 "event re-wiring")

static

직렬화기는 "객체 인스턴스"의 필드를 걷는 물건인데 
static은 인스턴스가 아니라 타입 소속이라 순회 대상에 없고

설령 저장한들 내용물이 대개 옛 세계의 객체·델리게이트 참조라 복원이 무의미

Unity의 선택은 복원이 아니라 재초기화(static 생성자 재실행, InitializeOnLoad로 재배선)

C++ 소멸자는 비동기 정리를 기다리는 단계로 나눌 수 없습니다
소멸자가 시작되면 한 번에 끝나야 합니다

반면 GPU나 오디오 자원은 다른 스레드에 해제를 요청한 뒤 fence 완료를 기다려야 할 수 있습니다

BeginDestroy             정리 시작
IsReadyForFinishDestroy  완료 여부 확인
FinishDestroy            최종 정리

비동기 정리를 시작하기 위한 함수
