lossyScale

부모들의 스케일과 회전을 전부 누적해서 계산해낸 값
표현 불가능한 것을 억지로 세 개의 숫자로 뭉갠 근사치이고, shear 성분이 버려집니다

Thus scale can not be represented correctly in a 3 component vector but only a 3x3 matrix
lossyScale is a convenience property that attempts to match the actual world scale as much as it can

If your objects are not skewed the value will be completely correct
계층에 비균등 스케일이 없거나 회전이 없으면 정확합니다

---

같은 것을 두 번 재는 것
하나의 대상을 두 가지 단위로 재고, 그 둘을 등호로 묶는 것

대상은 "카메라에 보이는 세로 구간"
이걸 두 번 잽니다

픽셀로 재면    →  Screen.height 픽셀
유닛으로 재면  →  orthographicSize × 2 유닛

같은 구간이므로 등호가 성립합니다
Screen.height 픽셀  =  (orthographicSize × 2) 유닛

---

Screen.height ÷ (orthographicSize × 2) 픽셀  =  1 유닛

"3피트 = 1야드니까 1야드는 3피트"

DisplayMetrics.densityDpi는 OEM이 빌드 설정에서 고른 값
실측 DPI가 410이어도 densityDpi는 480으로 보고될 수 있습니다

문서가 제시하는 대안이 xdpi/ydpi 평균
some Android devices might report incorrect xdpi and ydpi values

더 정확할 수도 있지만 신뢰할 수는 없다

iOS

Apple은 물리 DPI를 알려주는 API를 제공하지 않습니다
UIScreen이 주는 건 포인트 단위 크기와 scale(1x/2x/3x)뿐

scale은 논리 좌표와 하드웨어 픽셀의 비율이지 인치와는 무관

실질적으로는 기기 모델 식별자 → 알려진 DPI 테이블 조회에 의존하게 됩니다
기기 종류가 제한적이라 이 방식이 통하는 것

데스크톱

모니터의 EDID 블록

모니터가 케이블로 자기 정보를 보고할 때 
물리적 화면 크기를 cm 또는 mm 단위로 넣게 되어 있고, 
OS가 그걸 읽어 해상도와 나눠 DPI를 냅니다

문제는 이 필드가 비어 있거나 반올림되어 있거나 그냥 틀린 모니터가 흔하다는 것입니다
The property returns 0 if the current DPI cannot be determined

Windows의 "디스플레이 배율 125%"나 macOS의 Retina 스케일링은 물리적 DPI가 아닙니다
논리 좌표를 물리 픽셀로 늘리는 배율

Screen.dpi는 모바일에서만 조건부로 신뢰하고, 
데스크톱에서는 0이 나올 수 있다고 가정하고 코드를 짜야 합니다

float dpi = Screen.dpi;
if (dpi <= 0f) dpi = 96f;   // 폴백

Screen.currentResolution        // static. 메인 디스플레이 하나뿐

Display.displays[i].systemWidth // 인스턴스. 0~7 각각
Horizontal native display resolution

전자는 지금 설정된 모드, 후자는 패널 고유 해상도입니다

다만 LCD/OLED는 네이티브가 아닌 해상도에서 화질이 나빠지므로 대부분 네이티브로 씁니다

논리 좌표와 물리 픽셀

물리 픽셀은 실체가 있습니다
디스플레이 패널에 물리적으로 박혀 있는 발광 소자
실제로는 R/G/B 서브픽셀 묶음

4K 모니터에는 3840 × 2160개

---

논리 픽셀은 물건이 아니라 약속된 눈금
UI를 그릴 때 쓰는 좌표계의 한 칸
대응하는 물리적 실체가 존재하지 않습니다

화면 밀도가 제각각인 세상에서 
앱이 "버튼을 100픽셀로"라고 하드코딩하면, 
밀도가 두 배인 화면에서 버튼이 절반 크기로 쪼그라듭니다. 

앱을 고치지 않고 이 문제를 풀려면 
앱이 쓰는 좌표계와 하드웨어 좌표계를 분리하는 수밖에 없습니다

---

그래서 OS가 중간 좌표계를 하나 끼워 넣었습니다
앱은 논리 좌표로 그리고
컴포지터가 배율을 곱해 
물리 픽셀로 옮깁니다

---

물리 픽셀 = 논리 좌표 × 배율

Windows 125%면 논리 1 = 물리 1.25
macOS Retina 2x면 논리 1 = 물리 2입니다

---

논리 픽셀의 "크기"는 목표값

Windows       96 DPI 가 100% 기준
macOS point   1/72 인치 (활자 포인트에서 유래)
Android dp    1/160 인치 (mdpi 기준)
CSS px        1/96 인치 

---

CSS 사양은 참조 픽셀을 길이가 아니라 시야각으로 정의합니다
팔 길이(약 28인치) 거리에서 96 DPI 화면의 픽셀 하나가 차지하는 각도
원래 의도가 "물리적 크기"가 아니라 "사용자 눈에 이만큼으로 보였으면 좋겠다"

기준값이 72, 96, 160으로 제각각

---

Unity 플레이어는 DPI-aware로 동작해서, 

Screen.width는 논리 좌표가 아니라 
실제 백버퍼의 물리 픽셀 수입니다. 

OS의 논리 좌표 층을 건너뛰고 하드웨어 해상도로 직접 렌더합니다

---

텍셀 수         무차원 — 개수
월드 유닛       무차원 — 가상의 눈금
프레임버퍼 픽셀 무차원 — 개수
물리 픽셀       무차원 — 개수
논리 픽셀       무차원 — 약속된 눈금

---

단위는 "개"로 같습니다. 
다른 건 어느 배열을 세느냐입니다

Sprite.rect.width            텍스처 배열의 열 개수
Camera.scaledPixelWidth      실제로 셰이딩되는 배열의 열 개수
Camera.pixelWidth            카메라 뷰포트 배열의 열 개수
Screen.width                 메인 창 백버퍼 배열의 열 개수
Display.renderingWidth       그 디스플레이 렌더 타깃 배열의 열 개수
Display.systemWidth          패널 소자 배열의 열 개수
Screen.currentResolution.w   패널이 현재 모드에서 쓰는 열 개수

---

전부 "픽셀"이라 불리지만 
서로 다른 배열의 인덱스 공간

---

배율 — 개수를 개수로

Camera.rect               프레임버퍼 개수 → 뷰포트 개수
dynamic resolution 배율   뷰포트 개수 → 셰이딩 개수
OS 디스플레이 배율        논리 개수 → 물리 개수
디스플레이 스케일러       프레임버퍼 개수 → 패널 개수

---

(a) 버퍼/패널의 픽셀 개수       2560, 1440 같은 정수
(b) OS 배율 설정                100%, 125%, 2x
(c) 패널의 물리적 크기          "이 화면은 가로 59.8cm"

"못 믿는다"고 한 건 (c)
"Unity가 안다"고 한 건 (a)
"DPI-aware"라는 말이 실제로 가리키는 건 (b)

---

시스템이 반드시 알아야 작동하는 정보는 정확하고, 
몰라도 작동하는 정보는 부정확합니다.

(a)는 없으면 아무것도 안 됩니다
프레임버퍼를 할당하려면 몇 픽셀인지 알아야 합니다
메모리 크기 계산에 직접 들어가는 정수입니다

---

DPI-aware
이 프로세스는 OS의 자동 비트맵 확대를 거부하고, 배율을 직접 처리하겠다

DPI-aware가 아닌 프로세스에게 Windows는 거짓말을 합니다. 
2560×1440 화면에 125% 배율이면 
앱에게 "너 창은 2048×1152야"라고 알려주고, 
앱이 그 크기로 그린 결과를 
비트맵 확대해서 화면에 올립니다. 

옛날 앱이 고해상도 화면에서 뿌옇게 보이는 게 이것입니다.

---

DPI-aware인 프로세스에게는 거짓말을 안 합니다

클라이언트 영역의 실제 물리 픽셀 수를 그대로 알려주고
"UI 크기 조절은 네가 알아서 해라"가 됩니다

---

그러니 정확한 이름은 "scale-aware" 또는 "OS 확대 거부"에 가깝습니다. 
물리적 측정과는 아무 상관이 없습니다
