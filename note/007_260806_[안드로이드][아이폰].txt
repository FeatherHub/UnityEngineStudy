Unity Linker 단계 (code stripping)

Unity Linker는 진입점(entry point)에서 출발해 
정적으로 도달 가능한 타입과 메서드만 남기고 
나머지를 관리 어셈블리에서 삭제

리플렉션으로만 접근하는 타입은 Unity Linker가 도달 가능성을 추론하지 못해 삭제해 버린다
실행 시점에 TypeLoadException이나 MissingMethodException이 나는 원인이다

방지 수단은 link.xml 파일로 보존 대상을 명시하거나 [Preserve] 특성을 붙이는 것

il2cpp.exe 변환기 단계
축소된 관리 어셈블리를 읽어 두 종류의 산출물을 만든다

어셈블리 안의 메서드 하나가 C++ 함수 하나가 된다
MyPlayerController.Update() 메서드는 MyPlayerController_Update_m<해시>() 같은 이름의 C++ 자유 함수가 된다

클래스도 C++ 클래스가 되지 않는다. 
C# 타입은 C++ 구조체(struct)가 되고, 
C# 메서드는 첫 인자로 this 포인터를 명시적으로 받는 C++ 자유 함수가 된다

C++의 상속·가상 함수 기능을 쓰지 않는 이유는, 
.NET의 타입 시스템 의미론(인터페이스 디스패치, 제네릭, 박싱)을 
C++ 타입 시스템에 그대로 얹을 수 없기 때문

대신 libil2cpp 런타임이 자체 가상 함수 테이블을 관리한다

il2cpp.exe 변환기는 실제로 사용되는 제네릭 인스턴스마다 별도의 C++ 코드를 생성해야 한다

다만 참조 타입은 코드를 공유한다.
List<object>와 List<string>은 요소가 둘 다 포인터 크기이므로 같은 코드를 쓴다

문제는 빌드 시점에 발견할 수 없는 제네릭 인스턴스
이런 경우를 위해 IL2CPP scripting backend는 full generic sharing이라는 폴백을 만든다

---

C++ 코드와 libil2cpp 런타임에 재현해야 하는 managed semantics

자동 메모리 관리
Boehm-Demers-Weiser 가비지 컬렉터, write barrier

NullReferenceException을 던진다는 보장
IndexOutOfRangeException을 던진다는 보장
InvalidCastException을 던진다는 보장

정적 생성자 의미론 — 지연 실행, 정확히 1회, 스레드 안전
실행 시점 메타데이터 — 리플렉션이 타입 이름·필드·특성을 조회할 수 있어야 함

reified generics — 실행 시점에 typeof(T)가 실제 타입 인자를 알아야 함 (Java의 type erasure와 다르다)

박싱과 언박싱 — 값 타입을 object에 담을 때 힙 할당

인터페이스 디스패치와 가상 디스패치 — .NET 규칙에 따른 메서드 결정

---

il2cpp.exe 변환기는 C#의 의미론을 "C++라는 이식성 있는 어셈블리 언어 위에 재구현"한다

널 포인터 — C++는 검사하지 않는다

Foo* p = nullptr;
p->x = 1;         // 정의되지 않은 동작. C++ 예외 없음.

그 크래시를 일으키는 주체가 C++이 아니다.

1. CPU가 주소 0x0000 (+ 필드 오프셋) 에 쓰기를 시도
2. 해당 주소는 매핑되지 않은 페이지 → CPU가 page fault 발생
3. Windows 커널이 access violation (0xC0000005) 로 변환
4. Structured Exception Handling(SEH) 메커니즘으로 프로세스에 전달

이것은 C++ 예외가 아니기 때문에 이런 결과가 나온다

try {
    p->x = 1;             // p == nullptr
}
catch (...) {             // ← 표준 C++ 에서는 여기 안 걸린다
    // 도달하지 않음. 프로세스가 그냥 죽는다.
}

MSVC의 비표준 확장 /EHa를 쓰면 SEH를 catch(...)로 잡을 수 있지만,
Microsoft 자신이 권장하지 않는 방식이고 표준 동작이 아니다

---

오프셋이 크면 크래시하지 않는다. 
널 포인터에서 필드 오프셋이 충분히 크면(예: 큰 구조체의 뒤쪽 필드) 
접근 주소가 매핑된 메모리 영역에 착륙할 수 있다. 
그러면 크래시 없이 엉뚱한 메모리를 조용히 덮어쓴다

---

컴파일러가 검사를 지워버린다
정의되지 않은 동작은 "절대 일어나지 않는다"고 가정해도 되므로, 
컴파일러는 그 가정 위에서 최적화한다.

Foo* p = get();
int v = p->x;             // 여기서 역참조했다
if (p == nullptr) {       // ← 컴파일러: "이미 역참조했으니 p는 널일 수 없다"
    handle_error();       //    → 이 분기 전체를 삭제
}

CVE-2009-1897(Linux 커널 2.6.30, drivers/net/tun.c)

tun->sk를 먼저 역참조한 뒤 널 검사를 하는 코드였고,
GCC가 그 널 검사를 최적화로 제거했다

---

C#에서 arr[i]는 언어 명세가 IndexOutOfRangeException을 약속한다
C++에서 arr[i]는 아무것도 약속하지 않는다

il2cpp.exe 변환기가 NullCheck(t);라는 줄을 생성 C++ 코드에 명시적으로 써 넣는 이유
참조를 통한 모든 필드 접근에 조건 분기가 하나씩 붙는다

---

CoreCLR의 JIT 컴파일러는 명시적 널 검사를 거의 생성하지 않는다
cmp [rcx], ecx 같은 명령으로 일부러 하드웨어 접근 위반을 유발하고, 
런타임이 그 access violation(0xC0000005)을 가로채
NullReferenceException으로 변환한다

JIT이 할 수 있고 AOT는 못 하는 것

실제 CPU를 안다.

AOT 컴파일은 어떤 CPU에서 돌지 모르는 상태로 컴파일한다. 
따라서 기준 명령어 집합(baseline ISA)을 잡아야 한다. 
AVX-512가 있는 CPU에서 돌아도 쓰지 못한다.

JIT은 실행되는 그 기계 위에서 컴파일한다. 
그래서 .NET에서는 이런 코드가 성립한다

if (Avx2.IsSupported)
{
    // AVX2 경로
}
else
{
    // 폴백 경로
}

JIT은 Avx2.IsSupported를 컴파일 시점 상수로 접어버리고, 성립하지 않는 분기를 통째로 삭제한다
분기 비용이 0이 된다

Unity 생태계에서 이 공백을 메우려고 존재하는 것이 Burst 컴파일러

실제 실행 프로파일을 안다 (dynamic PGO)

CoreCLR의 tiered compilation

1단계 (tier-0)    빠르게 대충 컴파일. 대신 계측 코드를 심는다.
                  → 어느 호출 지점에서 실제로 어떤 타입이 오는지 기록
                  → 어느 분기가 실제로 얼마나 자주 참인지 기록
2단계 (tier-1)    자주 실행되는 메서드만 골라 재컴파일.
                  이때 1단계에서 수집한 실제 데이터를 사용.

---

여기서 나오는 최적화가 guarded devirtualization
인터페이스 호출 지점에서 실제로는 99% ConcreteEnemy 타입만 온다는 것을 관측했다면
JIT은 타입 검사 하나 + 직접 호출 + 인라이닝으로 바꿔버린다

static readonly 값을 상수로 접는다.

정적 생성자가 실행된 뒤에는 그 값이 다시는 바뀌지 않는다
tier-1 컴파일 시점에 이미 값을 알고 있으므로 상수로 접는다

CoreCLR이 Mono보다 나은 점

가비지 컬렉터의 근본적 차이

Boehm-Demers-Weiser GC (현재)
  - conservative : 스택의 값이 포인터인지 정수인지 구분 못 함
                   → 포인터처럼 생긴 정수 때문에 죽은 객체가 살아남음
  - non-moving   : 객체를 이동시키지 못함
                   → heap fragmentation 이 영구히 쌓임
  - non-generational (Unity 구성 기준)

CoreCLR GC
  - precise      : 어느 슬롯이 참조인지 정확히 안다
  - moving       : 객체를 이동·압축한다 → fragmentation 해소
  - generational : gen0 는 bump allocator + 짧은 수집

---

이식 작업의 대부분이 "관리 메모리가 네이티브 코드로 넘어가지 않게 한다"는 원칙으로 
bindings generator와 proxy generator를 고치는 일

객체가 이동해도 안전하려면 네이티브 쪽이 관리 객체 포인터를 들고 있으면 안 되기 때문

코드 리로드 모델

AppDomain 언로드 방식이 아니라 multi-ALC(AssemblyLoadContext) 기반으로 바뀐다

For Unity 6.8 we'll move to a multi-ALC based code reload system
The more finely grained we can made the ALC, the less code has to reload.

전부 내렸다 올리는 것이 아니라 바뀐 어셈블리만 갈아끼우는 방향이다
이터레이션 속도의 근본 개선이 여기서 나온다

---

The new CoreCLR runtime is compliant with the IEEE 754 standard for floating point operations
This may be different from what Mono's JIT produced

---

While we expect to use CoreCLR to bring code iteration time and runtime performance improvements over time, 
in Unity 6.8 we're aiming for holistic performance parity
some things will be faster, others slower, on balance about the same

We are explicitly delaying major performance optimization work 
until the subsequent LTS release following Unity 6.8 in 2027

그 시점에 얻는 것은 성능이 아니라 C# 14, .NET 10 API, 그리고 domain reload 없는 이터레이션

The CoreCLR GC uses a threshold of 85 kilobytes for large objects
There are no changes to behavior of the Boehm GC used by IL2CPP

precise, moving, generational, LOH 85 KB

IL2CPP Player (iOS/Android/콘솔) →  Boehm GC
conservative, non-moving, LOH 2~8 KB

What is the Dalvik VM?

It is a virtual machine to…

run on a slow CPU
with relatively little RAM
on an OS without swap space
while powered by a battery

메모리 제약  [일차]
  total system RAM                              64 MB
  available RAM after low-level startup         40 MB
  available RAM after high-level services       20 MB
  system library                          10 MB (jar)
  multiple independent mutually-suspicious processes
  separate address spaces, separate memory

CPU 제약  [일차]
  CPU speed      250-500 MHz
  bus speed      100 MHz
  data cache     16-32 KB

시스템 라이브러리 하나가 10 MB인데 앱이 쓸 수 있는 RAM 전체가 20 MB

메서드 swizzling

실행 중에 두 메서드의 구현을 서로 맞바꾸는 기법

C++ 의 가상 함수 호출
  컴파일 시점에 vtable 슬롯 번호가 정해진다
  → 실행 시점에는 그 슬롯을 읽어 점프할 뿐
  → 바꿀 수 없다

Objective-C 의 메시지 전달
  [obj doSomething]
      ↓  컴파일러가 이렇게 바꾼다
  objc_msgSend(obj, @selector(doSomething))
      ↓  실행 시점에 하는 일
  1. obj 의 클래스를 찾는다
  2. 그 클래스의 메서드 테이블에서 "doSomething" 이라는
     셀렉터(selector)에 대응하는 함수 포인터(IMP)를 찾는다
  3. 그 함수로 점프한다

---

Exceptions are forbidden in the kernel for reasons of both cost and stability. 
They increase the size of the code, thereby consuming precious kernel memory, 
and introduce unpredictable latencies. 

Further, because I/O Kit code may be invoked by many client threads, 
there's no way to guarantee that an exception will be caught

---

RTTI를 금지한 이유

"it doesn't support dynamic allocation of classes by name, 
a feature required for loading kernel extensions."

드라이버의 어떤 메서드 하나가 이런 다양한 경로로 호출된다

③ 인터럽트 컨텍스트에서 호출된 경우

BSD — Berkeley Software Distribution

1969  AT&T 벨 연구소에서 Unix 탄생
        │
        │  대학에 소스 코드를 저렴하게 배포
        ↓

        vi 에디터, C shell, TCP/IP 네트워크 스택, 가상 메모리
        이 개량판 배포본을 "Berkeley Software Distribution" 이라 부름

        ↓
      FreeBSD, NetBSD, OpenBSD 로 갈라짐
        └─ 그리고 Apple 의 Darwin (XNU) 이 여기서 코드를 가져감

BSD 라이선스는 매우 관대하다. "저작권 표시만 유지하면 뭘 하든 상관없다. 소스 공개 의무 없음"이 요지다.

GPL (Linux)   가져다 쓰고 고쳐서 배포하면 소스를 공개해야 한다
BSD 라이선스   가져다 쓰고, 고치고, 소스 안 열고 팔아도 된다

GCC의 GPLv3가 clang을 낳았고, 
BSD의 관대함이 Darwin을 가능하게 했다

Mach — 마이크로커널

1985~1994  Carnegie Mellon 대학에서 개발
             Richard Rashid, Avie Tevanian 주도
             Mach 3.0 이 진짜 마이크로커널
             │
1986       NeXT 엔지니어들이 UNIX 컨퍼런스에서 Mach 발표를 보고
             NeXT OS 에 쓰기로 결정
             │
           Tevanian 이 박사 논문을 마치고 NeXT 에 합류
             (Microsoft 제안을 거절하고)
             → core OS 팀 리드 → OS 그룹 매니저 → VP of Software
             │
1996~      Apple 이 NeXT 인수
             Tevanian 이 NeXTSTEP 을 macOS 로 재설계
             → XNU 커널이 macOS, iOS, iPadOS, tvOS, watchOS 의 기반

참고로 Rashid는 1991년 Microsoft로 가서 Microsoft Research를 창립했다

마이크로커널이라는 아이디어

모놀리식 커널 (Linux)
  ┌──────────────────────────────────┐
  │  커널 (특권 모드)                │
  │   파일시스템, 네트워크, 드라이버 │
  │   메모리 관리, 스케줄러 ...      │
  └──────────────────────────────────┘

빠르다 (함수 호출로 끝난다)
하나가 망가지면 커널 전체가 망가진다

Android — Unix UID를 재해석

Android            UID = 앱 하나          

앱 A → uid 10123, 데이터 디렉터리는 uid 10123 소유, 퍼미션 700
앱 B → uid 10124, 앱 A 의 디렉터리를 열려고 하면 EACCES

iOS — 별도의 샌드박스 층을 얹었다

코드 서명       실행되는 모든 코드가 Apple 이 인정한 서명을 가져야 한다

샌드박스 프로파일  프로세스가 호출할 수 있는 시스템 콜과 접근 가능한
                   경로를 커널 수준에서 제한

entitlement    앱이 가질 수 있는 특별 권한 목록. 서명에 박혀 있어
               실행 중에 위조할 수 없다

컨테이너        앱마다 자기 디렉터리만 보이고, 다른 앱의 경로는
                존재 자체를 알 수 없다

샌드박스가 추가로 하는 일

권한 시스템이 성립하게 만든다

"이 앱에 카메라 접근을 허용하시겠습니까?"라는 팝업이 성립하려면 
(a) 누가 요청하는지 식별할 수 있고
(b) 거부를 강제할 수 있어야 한다

샌드박스가 없으면
앱이 그냥 카메라 장치를 열어버리면 그만이다

---

  앱 하나에 취약점 발견 → 공격자가 코드 실행 획득
  → 하지만 그 앱의 컨테이너 안에 갇혀 있다
