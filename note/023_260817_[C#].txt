ref struct
정의는 "ref 필드를 담을 수 있는 struct"

여기서 ref T는 managed reference(CLR 용어로 byref)
객체 내부 중간을 가리킬 수도, 스택 프레임을 가리킬 수도, unmanaged 메모리를 가리킬 수도 있습니다

그런데 이런 byref는 힙 객체의 필드에 저장될 수 없습니다
힙 객체의 필드는 온전한 객체 참조여야만 GC가 compaction 시 갱신할 수 있습니다
스택 프레임을 가리키는 byref가 힙에 저장되면 그 프레임보다 오래 살아남아 dangling reference가 됩니다

---

ref를 담을 수 있다 (원인) → 그래서 힙에 올라가면 안 된다 (결과)

ALC — AssemblyLoadContext

.NET Framework에는 AppDomain이 있었습니다. 
어셈블리를 별도 도메인에 로드하고 도메인을 통째로 언로드할 수 있었고, 
Unity의 domain reload가 이 위에 서 있습니다
스크립트를 고치면 관리 도메인 전체를 날리고 다시 만드는 방식

.NET Core/CoreCLR에는 AppDomain 언로드가 없습니다
도메인은 하나뿐이고 언로드 불가입니다
대신 System.Runtime.Loader.AssemblyLoadContext가 들어왔습니다.

---

ALC는 어셈블리를 담는 스코프
isCollectible: true로 만들면 개별 ALC 단위로 언로드할 수 있습니다

핵심은 언로드가 강제가 아니라 협조적이라는 점입니다
ALC 안의 무언가가 바깥에서 참조되고 있으면 회수되지 않습니다

살아있는 객체 하나, static 루트 하나, 그 코드에 스택 프레임을 둔 스레드 하나, 델리게이트 하나만 남아도 언로드가 실패합니다

---

지금: 스크립트 하나만 고쳐도 관리 도메인 전체를 재구축 → domain reload가 느림

6.8: 어셈블리를 여러 ALC에 나눠 담고, 변경된 어셈블리를 담은 ALC(와 그에 의존하는 ALC)만 교체
"The more finely grained we can made the ALC, the less code has to reload"

---

언로드 실패 시 같은 타입이 두 벌 로드된다는 것

CoreCLR GC
precise, moving

---

CoreCLR에서는 성립하지 않으므로 표현을 셋으로 쪼갰습니다.

GC-allocated pointer — 기존 방식. 전환용 임시이고 최종 제거 대상

managed stack reference — 포인터 대신 포인터 변수의 주소를 넘깁니다. 
지역 주소는 GC가 옮기지 않고 관리 스택이 객체를 살려두므로 안전합니다. 

GCHandle — 강한 간접 참조. 확실하지만 생성/파괴 비용이 있어 꼭 필요한 곳에만

---

그리고 이 셋을 담는 ScriptingReferenceWrapper를 만들면서, 
포인터 정렬의 하위 2비트를 태그로 재사용해 크기를 uintptr_t 하나로 유지했습니다. 

기존 타입과 크기가 같아야 1:1 교체가 가능하기 때문입니다. 

---

추가로 managed↔native 경계 두 개(managed→native는 Bindings Generator, native→managed는 Proxy Generator)를 통째로 개조해서, 
GC 할당 객체가 경계를 넘지 못하게 하고 넘으면 진단을 내도록 만들었습니다.

---

fixed / GCHandleType.Pinned가 이제 의미를 갖습니다. 
전에는 사실상 no-op이었는데 이제 진짜 비용이 있고, 
핀이 많으면 gen0 압축을 방해해 데이터 지역성이 나빠집니다

---

conservative → precise 전환으로 객체 수명이 달라집니다. 
Boehm이 스택 오탐 덕에 우연히 살려두던 것들이 더 일찍 죽으면서 잠재 버그가 드러납니다

---

IL2CPP의 Boehm GC는 그대로 유지됩니다.

에디터 / CoreCLR 데스크톱 플레이어 → precise, moving
IL2CPP 빌드(모바일·콘솔·WebGL) → conservative, non-moving

같은 제품 안에 의미가 다른 두 GC가 공존하게 됩니다.
